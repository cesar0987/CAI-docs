# F9 — Endurecimiento y Operación Continua

> [!info] Objetivo
> **Que el sistema sobreviva al uso diario y a los incidentes que van a aparecer.**
> F8 puso el sistema en producción. F9 lo convierte en algo que **se puede sostener
> durante años** sin que el único que entienda el sistema sea la persona que lo escribió.

---

## 1. Duración

| Dedicación | Duración |
|---|---|
| 8 h/semana | ~2 semanas |
| 15 h/semana | ~1 semana |

> [!note] F9 no tiene fecha de fin
> Las tareas de esta fase son el **cuerpo del documento** del operativo. Lo que se
> implementa en F9 es el conjunto mínimo de controles que hay que tener **antes** de
> dejar de trabajar en el sistema y pasar a mantenerlo.

## 2. Tareas

### 2.1 PITR — Restauración punto en el tiempo

> [!danger] El backup diario solo protege contra la pérdida del día anterior
> Con un backup diario, el peor caso es perder **24 horas** de trabajo: todas las
> notas clínicas del día, todos los pagos del día. Con PITR, el peor caso es
> **1 hora**.

```bash
# /etc/postgresql/16/main/pgbackrest.conf
[global]
repo1-path=/var/lib/pgbackrest
repo1-cipher-type=aes-256-cbc
repo1-cipher-pass=<CLAVE_EN_GESTOR_DE_CONTRASENAS>

[main]
pg1-path=/var/lib/postgresql/16/main
pg1-port=5432
pg1-socket-path=/var/run/postgresql

# Retención: 14 diarios, 8 semanales, 12 mensuales
pg1-archive-retention-full=4
pg1-archive-retention-diff=14
pg1-archive-retention-type=full
```

```bash
# Backup base (una vez, al configurar)
pgbackrest --stanza=main --type=full backup

# Backup continuo (por cron)
pgbackrest --stanza=main --type=diff backup

# PITR: restaurar a las 14:32 del 12 de marzo
pgbackrest --stanza=main --type=time --target='2026-03-12 14:32:00' restore
```

**El `restore.cfg` que se genera:**

```text
restore_command = "cp /var/lib/pgbackrest/main/archive/%f %p"
recovery_target_time = '2026-03-12 14:32:00'
recovery_target_action = 'promote'
```

> [!important] El RPO y el RTO son promesas medibles
> | Métrica | Objetivo | Cómo se verifica |
> |---|---|---|
> | **RPO** (punto de pérdida de datos) | ≤ 1 hora | Con archiving continuo (`archive_timeout = 300`) |
> | **RTO** (tiempo de recuperación) | ≤ 4 horas | Ensayo completo documentado y cronometrado |
>
> El ensayo de PITR se hace **una vez al trimestre** y en cada cambio de versión de
> PostgreSQL. Un PITR no probado es una hipótesis.

**El `archive_timeout` es obligatorio:**

```sql
-- postgresql.conf
archive_mode = on
archive_command = 'pgbackrest --stanza=main archive-push %p'
archive_timeout = 300          -- 5 minutos: máximo 5 min de pérdida
wal_level = replica
```

> [!warning] `archive_timeout` tiene un costo
> Fuerza un switch de WAL cada 5 minutos. En un servidor modesto eso genera más
> archivos WAL y más I/O. Es el precio de un RPO de 5 minutos. Si el servidor no da
> cuenta, se sube a 900 (15 min) y se acepta el RPO correspondiente.

**Implementación con TOTP (una app en el teléfono):**

```bash
# En el servidor
sudo apt install php8.3-totp qrcode
```

```php
// packages/identity/src/Services/TotpService.php
declare(strict_types=1);

namespace Cai\Identity\Services;

use Illuminate\Support\Str;
use Illuminate\Support\Facades\Hash;
use OTPHP\OTPInterface;
use OTPHP\TOTP;

final class TotpService
{
    private readonly OTPInterface $totp;

    public function __construct(private readonly string $issuer, private readonly string $encryptionKey)
    {
        $this->totp = new TOTP(
            issuer: $issuer,
            label: '',
            digits: 6,
            period: 30,
            algorithm: 'sha1',
        );
    }

    /**
     * Genera el secreto y la URL para el código QR.
     *
     * @return array{secret: string, qr_url: string}
     */
    public function provision(string $username): array
    {
        $secret = $this->totp->generateSecret();

        return [
            'secret'  => $secret,
            'qr_url'  => $this->totp->getProvisioningUri(name: $username),
        ];
    }

    public function verify(string $secret, string $code): bool
    {
        if (! preg_match('/^\d{6}$/', $code)) {
            return false;
        }

        // Ventana de ±1 periodo (30 s antes y después): tolera relojes desfasados
        return $this->totp->verify(
            secret: $this->decrypt($secret),
            otp: $code,
            window: 1,
        );
    }

    /**
     * El secreto se guarda cifrado, igual que las notas clínicas.
     */
    private function encrypt(string $secret): string
    {
        return Crypt::encryptString($secret);
    }
}
```

**El flujo de verificación:**

```php
// packages/identity/src/Actions/VerifyMfaChallenge.php
final class VerifyMfaChallenge
{
    public function execute(VerifyMfaChallengeData $data): bool
    {
        $user = User::findOrFail($data->userId);

        if (! $user->mfa_enabled) {
            return true;   // Sin MFA: no hay nada que verificar
        }

        $record = DB::connection('identity')->table('mfa_challenges')
            ->where('user_id', $user->id)
            ->where('expires_at', '>', now())
            ->orderByDesc('created_at')
            ->first();

        if ($record === null) {
            return false;
        }

        // Un código no se puede reutilizar dentro de su ventana
        $verified = $this->totp->verify(
            secret: $user->mfa_secret,
            otp: $data->code,
            window: 1,
        );

        if (! $verified) {
            // Contar intentos fallidos
            DB::connection('identity')->table('mfa_challenges')
                ->where('id', $record->id)
                ->update(['attempts' => DB::raw('attempts + 1')]);

            return false;
        }

        DB::connection('identity')->table('mfa_challenges')
            ->where('id', $record->id)
            ->update(['verified_at' => now()]);

        return true;
    }
}
```

**Los códigos de recuperación:**

```php
// 10 códigos de un solo uso, en texto plano, se muestran UNA vez
// Se guardan hasheados (bcrypt), igual que una contraseña
```

> [!danger] El flujo de recuperación de MFA es un agujero potencial
> Si el único camino para recuperar el acceso a una cuenta con MFA es que alguien
> desactive el MFA, entonces el MFA no agrega seguridad: agrega un procedimiento
> administrativo. Por eso:
>
> | Regla | Detalle |
> |---|---|
> | Solo Dirección puede resetear MFA | Con registro en la auditoría |
> | Resetear MFA requiere identificar al usuario en persona | No por teléfono ni por email |
> | El reset **invalida** todos los códigos de recuperación | Los anteriores quedan inservibles |
> | Se genera un conjunto nuevo | Y se vuelve a hacer el proceso de alta |
> | Queda registrado quién, cuándo y por qué | Auditoría con motivo |
>
> Ver [[02.06 Modelo de Autorización y Permisos]].

### 2.3 Rate limiting en el login

```php
// routes/web.php o app/Providers/RouteServiceProvider.php
Route::post('/login', [AuthenticatedSessionController::class, 'store'])
    ->middleware([
        'guest',
        'throttle:5,1',      // 5 intentos por minuto por IP
    ]);
```

```php
// packages/identity/src/Actions/AttemptLogin.php
final class AttemptLogin
{
    public function execute(AttemptLoginData $data): LoginResult
    {
        // 1. Límite por IP (capa de infraestructura, antes de tocar la BD)
        // 2. Límite por cuenta (capa de aplicación)
        $attempts = DB::connection('identity')->table('login_attempts')
            ->where('identifier', $data->identifier)
            ->where('attempted_at', '>', now()->subMinutes(15))
            ->count();

        if ($attempts >= 5) {
            throw new TooManyLoginAttemptsException(
                'Demasiados intentos. Intenten de nuevo en 15 minutos.'
            );
        }

        // 3. Credenciales
        $user = User::where('email', $data->email)->first();

        if (! $user || ! Hash::check($data->password, $user->password)) {
            // Tiempo constante: se verifica igual aunque el usuario no exista
            Hash::check($data->password, '$2y$12$dummy.hash.that.is.always.wrong.....................');

            $this->recordAttempt($data, success: false);

            throw new InvalidCredentialsException('Credenciales incorrectas.');
        }

        // 4. Estado de la cuenta
        if ($user->locked_until !== null && $user->locked_until->isFuture()) {
            throw new AccountLockedException(
                'La cuenta está bloqueada temporalmente. Contacte al administrador.'
            );
        }

        // 5. MFA (si corresponde)
        if ($user->mfa_enabled) {
            return LoginResult::requiresMfa($user, $this->createChallenge($user));
        }

        $this->recordAttempt($data, success: true);

        return LoginResult::authenticated($user);
    }
}
```

**La cuenta se bloquea:**

| Intentos fallidos en 15 min | Acción |
|---|---|
| 1–4 | Se registra el intento, se muestra el mensaje genérico |
| 5–9 | Se bloquea la cuenta 15 minutos |
| 10+ | Se bloquea y **se notifica a Dirección** |

> [!important] El mensaje siempre es genérico
> "Credenciales incorrectas" es la misma respuesta si el email no existe o si la
> contraseña está mal. revelar si el email existe sería un **enumerador de cuentas**:
> permitiría a un atacante saber a quién atacar.

### 2.4 Cabeceras de seguridad y CSP

```nginx
# /etc/nginx/sites-available/cai
server {
    listen 443 ssl http2;
    server_name cai.centro.local;

    # --- Cabeceras de seguridad ---
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "DENY" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    add_header Permissions-Policy "geolocation=(), microphone=(), camera=()" always;
    add_header Content-Security-Policy "default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'" always;

    # --- No exponer la versión ---
    server_tokens off;
    fastcgi_hide_header X-Powered-By;
}
```

> [!note] Por qué `'unsafe-inline'` en `script-src`
> Filament v3 y Livewire usan scripts inline. La CSP estricta (`'none'`) rompe el
> panel. La solución correcta son **nonces**, pero requiere modificar la integración
> de Livewire. Es un ítem del backlog de endurecimiento.
>
> El objetivo de esta fase no es la CSP perfecta: es tener **las cabeceras
> presentes**, lo que bloquea los ataques más comunes (clickjacking, sniffing,
> referrer leakage).

> [!important] Por qué `queue:restart` es obligatorio
> Los workers de cola tienen el código viejo en memoria. Sin `queue:restart`, un
> worker puede estar ejecutando la versión anterior de una Action que ya cambió,
> con un esquema de datos nuevo. Es una de las causas más comunes de "en producción
> no funciona y en desarrollo sí".

### 2.6 Monitoreo de disco y errores

**El script de healthcheck ampliado:**

```bash
#!/usr/bin/env bash
# scripts/healthcheck.sh
set -euo pipefail

STATUS=0
REPORT=""

check() {
    local name="$1"; shift
    if "$@" >/dev/null 2>&1; then
        REPORT="${REPORT}OK   ${name}\n"
    else
        REPORT="${REPORT}FAIL ${name}\n"
        STATUS=1
    fi
}

check_php() {
    local name="$1"; local url="$2"
    local code
    code=$(curl -sk -o /dev/null -w "%{http_code}" --max-time 10 "$url" || echo 000)
    if [[ "$code" == "200" ]]; then
        REPORT="${REPORT}OK   ${name} (HTTP ${code})\n"
    else
        REPORT="${REPORT}FAIL ${name} (HTTP ${code})\n"
        STATUS=1
    fi
}

# --- Base de datos ---
check "PostgreSQL responde"    psql -tAc "SELECT 1" -U cai -d cai
check "Migraciones aplicadas"   php artisan migrate:status --no-ansi >/dev/null

# --- Disco ---
DISK_USE=$(df -h /srv/cai | awk 'NR==2 {print $5}' | tr -d '%')
if [[ "$DISK_USE" -lt 80 ]]; then
    REPORT="${REPORT}OK   Disco (${DISK_USE}%)\n"
else
    REPORT="${REPORT}FAIL Disco (${DISK_USE}%) > 80%\n"
    STATUS=1
fi

# --- Backups ---
BACKUP_AGE=$(( ( $(date +%s) - $(stat -c %Y /var/backups/cai/latest.dump 2>/dev/null || echo 0) ) / 3600 ))
if [[ "$BACKUP_AGE" -lt 26 ]]; then
    REPORT="${REPORT}OK   Backup local (${BACKUP_AGE}h)\n"
else
    REPORT="${REPORT}FAIL Backup local (${BACKUP_AGE}h) > 26h\n"
    STATUS=1
fi

# --- Aplicación ---
check_php "Aplicación" "https://cai.centro.local/up"

# --- Cola ---
QUEUE_FAILED=$(psql -tAc "SELECT count(*) FROM notifications.notification_deliveries WHERE status='failed'" -U cai -d cai 2>/dev/null || echo 0)
if [[ "$QUEUE_FAILED" -lt 10 ]]; then
    REPORT="${REPORT}OK   Notificaciones fallidas (${QUEUE_FAILED})\n"
else
    REPORT="${REPORT}WARN Notificaciones fallidas (${QUEUE_FAILED})\n"
fi

printf "%b" "$REPORT"
exit $STATUS
```

**Las alertas:**

| Alerta | Umbral | Severidad | Destino |
|---|---|---|---|
| Backup local fallido | > 26 h desde el último | 🔴 Crítica | Email a Dirección + Backup Custodian |
| Backup externo fallido | > 26 h desde el último | 🔴 Crítica | Email + teléfono |
| Disco > 80 % | 80 % | 🟡 Advertencia | Email al admin técnico |
| Disco > 90 % | 90 % | 🔴 Crítica | Email + teléfono |
| Error 500 en el log | > 5 en 1 h | 🔴 Crítica | Email al admin técnico |
| Migración pendiente | Alguien despliega sin migrar | 🔴 Crítica | Email al admin técnico |
| Healthcheck fallido | 3 intentos seguidos | 🔴 Crítica | Email + teléfono |
| Cola con fallos | > 10 pendientes en error | 🟡 Advertencia | Email al admin técnico |

> [!danger] La alerta de backup es la más importante
> Un backup que falla **en silencio** es peor que no tener backup: da una falsa
> sensación de seguridad. La alerta debe dispararse **cuando falla**, no cuando el
> backup deja de existir.

**La consulta de permisos excesivos:**

```sql
-- Usuarios con permisos que su rol no debería tener
SELECT u.id, u.email, r.name AS rol, p.name AS permiso
FROM identity.users u
JOIN identity.user_roles ur ON ur.user_id = u.id
JOIN identity.roles r ON r.id = ur.role_id
JOIN identity.role_has_permissions rp ON rp.role_id = r.id
JOIN identity.permissions p ON p.id = rp.permission_id
WHERE u.deleted_at IS NULL
  AND p.name LIKE 'care.%'      -- Permisos clínicos
  AND r.name NOT IN ('profesional', 'coordinacion', 'direccion')
GROUP BY u.id, u.email, r.name, p.name;
```

### 2.8 El "día del administrador"

Una sesión de mantenimiento de **medio día**, una vez por trimestre:

| Bloque | Duración | Contenido |
|---|---|---|
| Estado del sistema | 30 min | Versión desplegada, PHP/PostgreSQL, patches pendientes |
| Backups | 30 min | Verificar backup local, externo, y **hacer un ensayo de restauración** |
| Disco | 30 min | Limpiar releases antiguos, logs rotados, archivos temporales |
| Base de datos | 45 min | `VACUUM ANALYZE`, revisar tamaño de índices, `REINDEX` si hace falta |
| Dependencias | 45 min | `composer outdated`, `npm outdated`, CVEs conocidas |
| Sistema operativo | 30 min | `apt list --upgradable`, patches de seguridad |
| Permisos | 30 min | Revisión trimestral de la matriz |
| Documentación | 30 min | Actualizar el runbook con lo que cambió |
| **Total** | **4.5 h** | |

### 2.9 El plan de continuidad

> [!important] ¿Qué pasa si el dev no está disponible?
> El sistema no puede depender de una sola persona. El runbook ([[10.01 Runbook Operativo]])
> existe para eso. Pero hay una pregunta más grande:

| Pregunta | Respuesta recomendada |
|---|---|
| ¿Quién administer el servidor si el dev no está? | El **Administrador Técnico** (rol interno del centro), con el runbook |
| ¿Quién puede resetear MFA y crear usuarios? | El Administrador Técnico, siguiendo el procedimiento documentado |
| ¿Quién decide qué se implementa? | Dirección, con el backlog priorizado |
| ¿Quién restaura el backup? | Cualquiera con acceso al servidor, siguiendo el runbook |
| ¿Quién aprueba una migración de datos? | Dirección |

> [!danger] El bus factor de 1
> Hoy el único que entiende el sistema es el dev. Eso es un **riesgo operativo
> real**, no un detalle. Mitigaciones:
>
> | Mitigación | Cuándo |
> |---|---|
> | Runbook completo y probado | F8 (es entregable de F8) |
> | El Administrador Técnico hace la capacitación de 180 min | F8 |
> | Documentación de arquitectura accesible para el personal técnico | F9 |
> | Que el backup y la restauración no dependan de una persona | F9 (el script hace todo) |
>
> **Que la operación de rutina no dependa del dev es un requisito**, no una cortesía.

## 5. Riesgos

| Riesgo | Mitigación |
|---|---|
| `pgBackRest` no compila o falla en el servidor del centro | Probarlo **en F0**, no en F9. Si no funciona, PITR queda como pendiente y el RPO sigue en 24 h |
| La configuración de PITR nunca se prueba | Ensayo trimestral con acta, en el calendario de [[10.02 Calendario de Checklists]] |
| El MFA molesta al personal y pide que se desactive | Solo cuentas privilegiadas; hasta 3 códigos de recuperación; los profesionales no lo necesitan en el MVP |
| El rate limiting bloquea a usuarios legítimos que se olvidan la contraseña | 15 minutos de bloqueo, aviso claro, y un proceso de reset documentado |
| La CSP con `'unsafe-inline'` no aporta mucho | Es una mejora parcial y consciente. El CSP con nonces queda en el backlog |
| `queue:restart` no se ejecuta en algún deploy | Está en `release.sh`, que es el único camino de despliegue |
| El dev se va y el centro no puede operar | Runbook + capacitación del Administrador Técnico (obligatorios) |
| Nadie lee las alertas | La alerta de backup va a **dos** personas (Dirección + Backup Custodian) |
