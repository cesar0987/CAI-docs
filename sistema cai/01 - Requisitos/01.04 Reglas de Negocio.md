# Reglas de Negocio

> [!warning] Estado
> Este documento está en **borrador**. Las reglas marcadas con `❓ PENDIENTE` necesitan
> confirmación de Dirección antes de implementarse. Ver
> [[01.07 Preguntas Abiertas y Decisiones Pendientes]].

---

## 1. Alumnos

| # | Regla | Validación |
|---|---|---|
| RN-001 | Todo alumno tiene un **código único y estable** con formato `ALU-####`. El código no se reutiliza ni se modifica, aunque el alumno se dé de baja. | Unique en DB + generador con secuencia |
| RN-002 | Un alumno no puede tener fecha de nacimiento futura. | Regla de validación |
| RN-003 | Un alumno no puede tener dos tutor principales activos a la vez. | Restricción parcial en DB |
| RN-004 | Un tutor no puede estar vinculado dos veces al mismo alumno. | PK compuesta `student_guardians` |
| RN-005 | Un alumno **activo** debe tener al menos un tutor y al menos una matrícula activa antes de que se le programe una sesión. | Validación en el flujo de programación |
| RN-006 | Solo un tutor puede tener `is_primary = true` y `receives_admin_messages = true` a la vez. | Restricción parcial |
| RN-007 | Un alumno se da de baja con `status = 'inactive'` o `'withdrawn'`. **Nunca se elimina** si tiene historial (sesiones, notas, cargos). | `ON DELETE RESTRICT` en FKs + soft delete |
| RN-008 | La edad del alumno se **deriva** de la fecha de nacimiento; no se almacena. | Cálculo en el modelo |

## 2. Cuentas familiares

| # | Regla | Validación |
|---|---|---|
| RN-010 | Una cuenta familiar tiene un código único `FA-####`. | Unique |
| RN-011 | Un alumno pertenece a **una sola cuenta familiar activa** a la vez. | Restricción de exclusión en PostgreSQL sobre el rango de vigencia |
| RN-012 | Al cambiar de cuenta, la pertenencia anterior se **cierra** (se completa `valid_until`), nunca se borra. | Trigger / lógica de dominio |
| RN-013 | Una cuenta familiar debe tener **al menos un responsable de pago**. | Validación |
| RN-014 | Una cuenta familiar sin alumnos activos se marca `status = 'inactive'`, no se elimina. | Proceso |
| RN-015 | Los hermanos pueden estar en cuentas **distintas** si la familia así lo decide (p. ej. porque uno paga con otra cuenta). | Permitido; cada alumno tiene su cuenta activa |
| RN-016 | El saldo de una cuenta es la suma de los saldos de sus alumnos, **más ajustes de la cuenta**. | Cálculo |

> [!important] RN-011 en detalle
> La restricción de exclusión en PostgreSQL se implementa sobre un rango `daterange`:
> un alumno no puede tener dos filas de `family_account_members` con rangos que se
> solapen y `valid_until IS NULL` o posterior a la nueva `valid_from`.

## 3. Servicios, profesionales y matrículas

| # | Regla | Validación |
|---|---|---|
| RN-020 | Un servicio tiene nombre único y duración por defecto > 0. | Unique + check |
| RN-021 | Un servicio inactivo no admite nuevas matrículas, pero las existentes siguen vigentes. | Validación en la acción de matricular |
| RN-022 | Una matrícula tiene `end_date >= start_date`. | Check en DB |
| RN-023 | Un alumno no puede tener dos matrículas **activas** al mismo tiempo para el **mismo servicio**. | Restricción de exclusión por rango |
| RN-024 | Un profesional puede tener muchos alumnos; un alumno, muchos profesionales. | N:N con asignación |
| RN-025 | La asignación profesional↔alumno tiene vigencia (`from_date`, `to_date`). | Rango + índice |
| RN-026 | Solo un profesional puede ser **responsable** de un plan de atención a la vez. | Partial unique |

## 4. Grupos y sesiones

| # | Regla | Validación |
|---|---|---|
| RN-030 | Una sesión tiene `ends_at > starts_at`. | Check en DB |
| RN-031 | Un profesional **no puede** tener dos sesiones que se solapen en el tiempo, sin importar el servicio. | `EXCLUDE USING gist` sobre `(professional_id, tstzrange(starts_at, ends_at))` |
| RN-032 | La capacidad de un grupo no puede ser superada. | Validación al agregar participantes + check al contar |
| RN-033 | Un participante no aparece dos veces en la misma sesión. | `UNIQUE(session_id, student_id)` |
| RN-034 | Un participante de una sesión grupal debe tener una matrícula activa del servicio correspondiente. | Validación |
| RN-035 | La asistencia se registra contra el **participante**, no contra el alumno ni contra el día. | FK a `session_participants` con `UNIQUE` |
| RN-036 | Solo existe **un** registro de asistencia por participante. | `UNIQUE(participant_id)` |
| RN-037 | Cancelar una sesión **no** borra los participantes ni las asistencias ya registradas; cambia su estado. | Máquina de estados |
| RN-038 | Una sesión reprogramada se crea como **sesión nueva** enlazada a la original (`rescheduled_from_id`), y la original pasa a `rescheduled`. | FK |
| RN-039 | Una sesión de recuperación (`makeup`) es una sesión nueva con su propia asistencia. | Tipo de sesión |
| RN-040 | El profesional responsable puede registrar la asistencia de **su** sesión. | Policy |
| RN-041 | Registrar asistencia sobre una sesión ya `completed` requiere un motivo y queda auditado. | Validación + auditoría |

## 5. Planes de atención y notas clínicas

| # | Regla | Validación |
|---|---|---|
| RN-050 | Un plan de atención tiene `start_date <= end_date` (si tiene fin). | Check |
| RN-051 | Solo el autor puede editar una nota en `draft`. | Policy |
| RN-052 | Una nota `finalized` **no se edita**. La corrección se hace con una nota nueva que referencia la original (`supersedes_note_id`) y un motivo. | Máquina de estados + FK |
| RN-053 | El contenido de una nota clínica se almacena **cifrado**. | Cast `encrypted` |
| RN-054 | Los metadatos (alumno, autor, tipo, fecha, estado) se almacenan **en claro** para permitir filtrado e indexado. | Diseño de columnas |
| RN-055 | Un profesional solo ve notas de alumnos con **asignación vigente**. | Policy |
| RN-056 | El autor de una nota la ve siempre, independientemente de la asignación vigente. | Policy |
| RN-057 | Un grant de acceso excepcional requiere: motivo, fecha de expiración y usuario que lo autoriza. | Validación + `security_events` |
| RN-058 | Un grant expirado no da acceso. | Verificación de `expires_at` en la Policy |
| RN-059 | Toda lectura de una nota clínica queda registrada en auditoría con: usuario, nota, alumno, fecha, motivo si aplica. | Observer + `audit_events` |
| RN-060 | Las notas clínicas **no** aparecen en exportaciones administrativas, widgets generales ni búsquedas globales. | Restricción de la capa de reportes + test |

## 6. Finanzas

| # | Regla | Validación |
|---|---|---|
| RN-070 | Todo cargo pertenece a **una cuenta familiar** y a **un alumno**. | FKs |
| RN-071 | Un cargo tiene importe > 0, vencimiento y período. | Checks |
| RN-072 | Los cargos se generan desde un plan de cuota vigente; los cargos manuales requieren autorización y motivo. | Acción de dominio |
| RN-073 | Un pago tiene importe > 0, método, fecha y usuario que lo registró. | Checks |
| RN-074 | **La suma de imputaciones de un pago no puede superar el importe del pago.** | Check en la acción + validación de DB |
| RN-075 | **La suma de imputaciones de un cargo no puede superar el importe del cargo.** | Check en la acción + validación de DB |
| RN-076 | Un pago sin imputar es un **pago a favor** (crédito) de la cuenta, y se refleja como tal en el estado de cuenta. | Cálculo |
| RN-077 | Registrar un pago, imputarlo y emitir el recibo ocurre en **una sola transacción**. | `DB::transaction` |
| RN-078 | La numeración de recibos es **correlativa y sin huecos**. | `receipt_sequences` con `SELECT ... FOR UPDATE` |
| RN-079 | Anular un pago **no** borra sus imputaciones: las conserva y las marca. La anulación libera el saldo. | `status = 'voided'` |
| RN-080 | Un recibo anulado conserva su número; el número no se reutiliza. | Unique + `status` |
| RN-081 | El saldo se **calcula**, nunca se escribe. | Diseño: no existe columna de saldo |
| RN-082 | Todo importe se guarda como `NUMERIC(14,2)` y se manipula con aritmética decimal (`bcmath`), nunca con `float`. | Columnas + casts |
| RN-083 | La moneda del sistema es PYG. No hay conversión de moneda en el MVP. | Constante |
| RN-084 | Un ajuste o descuento requiere autorización y motivo; queda auditado. | Acción + auditoría |
| RN-085 | Un profesional y un administrador financiero **no** pueden tener rol simultáneo salvo autorización expresa de Dirección, auditada. | Procedimiento + check al asignar roles |

## 7. Documentos y consentimientos

| # | Regla | Validación |
|---|---|---|
| RN-090 | Ningún documento se almacena en el directorio público. | Ruta de storage privada + test |
| RN-091 | Cada documento tiene: categoría, alumno asociado (o entidad), nombre original, mime, tamaño, hash y usuario que lo subió. | Columnas obligatorias |
| RN-092 | La descarga de un documento verifica el permiso **en cada solicitud**. | Ruta autenticada + Policy |
| RN-093 | Cada descarga queda auditada. | `document_access_events` |
| RN-094 | Un consentimiento tiene versión, fecha, texto y evidencia (documento firmado). | Columnas + documento |
| RN-095 | Un alumno no puede recibir atención sin consentimiento vigente de al menos un tutor responsable. | Validación en la programación de sesiones |
| RN-096 | Los documentos clínicos tienen una categoría que fuerza verificación de rol clínico. | Categoría → permiso |

## 8. Usuarios, roles y auditoría

| # | Regla | Validación |
|---|---|---|
| RN-100 | Todo usuario tiene exactamente un rol principal. | Validación |
| RN-101 | Un usuario desactivado no puede iniciar sesión, pero su historial se conserva. | `status` + revocación de sesión |
| RN-102 | Las acciones de alto impacto (anulación de pago, grant de acceso, cambio de rol, edición de nota finalizada) exigen **motivo**. | Validación |
| RN-103 | `audit_events` es **append-only**: nadie lo modifica ni lo borra. | Sin `updated_at`, sin delete |
| RN-104 | La auditoría se escribe en la **misma transacción** que la operación auditada. | Misma conexión + transacción |
| RN-105 | Toda contraseña es hash con bcrypt/argon2. Nunca se almacena en claro ni se registra en logs. | Implementación de Laravel |
| RN-106 | Los intentos de acceso fallidos se registran y se limitan (rate limiting). | Laravel throttle |
| RN-107 | Las cuentas privilegiadas (Dirección, Administración Técnica) requieren MFA. | Configuración |

|---|---|---|
