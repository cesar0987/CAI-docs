# Configuración de PostgreSQL

> [!important] Enfoque
> PostgreSQL está optimizado para un volumen pequeño de datos con muchas consultas
> complejas: exactamente el caso de este sistema. No se partitiona, no se replica (en el
> MVP) y no se usa una arquitectura distribuida. **Un solo servidor, bien configurado.**

---

## 1. Versión y configuración base

| Parámetro | Valor | Motivo |
|---|---|---|
| Versión | 16.x | LTS, rendimiento superior a 14, `MERGE`, mejor `VACUUM` |
| `listen_addresses` | `localhost` | La base no se expone a la red |
| `port` | 5432 | Estándar |
| `max_connections` | 100 | Suficiente para 30 usuarios concurrentes + jobs |
| `shared_buffers` | 512 MB (25% de 2 GB) | Caché principal de PostgreSQL |
| `effective_cache_size` | 2 GB | Optimización del planificador |
| `work_mem` | 16 MB | Suficiente para las consultas del sistema |
| `maintenance_work_mem` | 128 MB | Para índices y `VACUUM` |
| `wal_buffers` | 16 MB | Default × 2 |

```ini
# /etc/postgresql/16/main/postgresql.conf
listen_addresses = 'localhost'
max_connections = 100

shared_buffers = 512MB
effective_cache_size = 2GB
work_mem = 16MB
maintenance_work_mem = 128MB
wal_buffers = 16MB

# Query planner
random_page_cost = 1.1        # SSD: el costo de I/O aleatorio es bajo
effective_io_concurrency = 200
default_statistics_target = 100

# WAL y durability
wal_level = replica
max_wal_size = 2GB
min_wal_size = 128MB
checkpoint_completion_target = 0.9
checkpoint_timeout = 15min
archive_mode = on
archive_command = 'test ! -f /srv/cai/backups/wal/%f && cp %p /srv/cai/backups/wal/%f'

# Locale
lc_messages = 'es_PY.UTF-8'
lc_monetary = 'es_PY.UTF-8'
lc_numeric = 'es_PY.UTF-8'
lc_time = 'es_PY.UTF-8'
default_text_search_config = 'pg_catalog.spanish'

# Logging
log_min_duration_statement = 500    # Loguea consultas > 500 ms
log_line_prefix = '%m [%p] %u@%d '
log_checkpoints = on
log_connections = off
log_disconnections = off
log_lock_waits = on
deadlock_timeout = 1s

# Autovacuum (importante para las tablas de auditoría)
autovacuum = on
autovacuum_max_workers = 3
autovacuum_naptime = 60s
autovacuum_vacuum_scale_factor = 0.1
autovacuum_analyze_scale_factor = 0.05
```

## 2. Roles y permisos

### 2.1 Los tres roles

| Rol | Para qué | Puede |
|---|---|---|
| `cai_owner` | Dueño de los objetos (migraciones) | Todo en los schemas del sistema |
| `cai` | **Rol de la aplicación** | Solo lo necesario |
| `cai_readonly` | Reportes y auditoría | Solo `SELECT` |

```sql
-- Crear los roles
CREATE ROLE cai_owner WITH LOGIN PASSWORD 'CAMBIAR_1';
CREATE ROLE cai WITH LOGIN PASSWORD 'CAMBIAR_2';
CREATE ROLE cai_readonly WITH LOGIN PASSWORD 'CAMBIAR_3';

-- El rol de la aplicación solo tiene lo necesario
GRANT CONNECT ON DATABASE cai TO cai;
GRANT USAGE ON SCHEMA identity, students, scheduling, care, billing,
                        documents, notifications, reporting TO cai;

-- Permisos por tabla (DML básico)
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA identity, students,
     scheduling, billing, documents, notifications, reporting TO cai;
GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA care TO cai;

-- Sequences (necesario para las columnas SERIAL / BIGSERIAL)
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA identity, students, scheduling,
     care, billing, documents, notifications, reporting TO cai;

-- Funciones
GRANT EXECUTE ON ALL FUNCTIONS IN SCHEMA public TO cai;

-- Permisos por defecto para objetos futuros (creados por migraciones)
ALTER DEFAULT PRIVILEGES IN SCHEMA identity, students, scheduling, care, billing,
     documents, notifications, reporting
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO cai;
ALTER DEFAULT PRIVILEGES IN SCHEMA identity, students, scheduling, care, billing,
     documents, notifications, reporting
    GRANT USAGE, SELECT ON SEQUENCES TO cai;
```

### 2.2 La protección de la auditoría

> [!danger] El rol de la aplicación NO puede borrar la auditoría
> Es una de las pocas restricciones que vale la pena poner a nivel de base de datos,
> porque protege la evidencia.

```sql
-- Revocar DELETE sobre las tablas de auditoría
REVOKE DELETE ON identity.audit_events FROM cai;
REVOKE DELETE ON identity.security_events FROM cai;
REVOKE DELETE ON documents.document_access_events FROM cai;

-- Tampoco TRUNCATE
REVOKE TRUNCATE ON identity.audit_events FROM cai;

-- Verificación
SELECT has_table_privilege('cai', 'identity.audit_events', 'DELETE');
-- Debe devolver FALSE
```

**Test automatizado:**

```php
it('does not allow the application to delete audit events', function () {
    expect(DB::connection('identity')->table('audit_events')->getConnection()
        ->getPdo()
        ->prepare('DELETE FROM identity.audit_events WHERE id = -1')->execute())
        ->toBeFalse();
});
```

> [!note] `REVOKE` no impide `TRUNCATE` si se tiene `TRUNCATE` heredado
> PostgreSQL tiene `TRUNCATE` como un permiso separado. Ambos se revocan explícitamente.

### 2.3 Permisos por tabla (granularidad fina)

Para las tablas más sensibles:

```sql
-- La aplicación no puede modificar la auditoría, solo insertar y leer
GRANT SELECT, INSERT ON identity.audit_events TO cai;
GRANT SELECT, INSERT ON identity.security_events TO cai;

-- Los cobros: no se pueden borrar pagos
GRANT SELECT, INSERT, UPDATE ON billing.payments TO cai;
REVOKE DELETE ON billing.payments FROM cai;

-- Las notas clínicas: no se pueden borrar
GRANT SELECT, INSERT, UPDATE ON care.clinical_notes TO cai;
REVOKE DELETE ON care.clinical_notes FROM cai;
```

### 3.2 El `search_path` por conexión

Cada módulo usa su propia conexión de Laravel con un `search_path` distinto:

```php
// config/database.php
'connections' => [
    'pgsql' => [
        'driver' => 'pgsql',
        'host' => env('DB_HOST', '127.0.0.1'),
        'port' => env('DB_PORT', '5432'),
        'database' => env('DB_DATABASE', 'cai'),
        'username' => env('DB_USERNAME', 'cai'),
        'password' => env('DB_PASSWORD'),
        'charset' => 'utf8',
        'prefix' => '',
        'prefix_indexes' => true,
        'search_path' => 'public',
        'sslmode' => 'prefer',
    ],

    'identity' => [
        'driver' => 'pgsql',
        'host' => env('DB_HOST', '127.0.0.1'),
        'port' => env('DB_PORT', '5432'),
        'database' => env('DB_DATABASE', 'cai'),
        'username' => env('DB_USERNAME', 'cai'),
        'password' => env('DB_PASSWORD'),
        'charset' => 'utf8',
        'prefix' => '',
        'prefix_indexes' => true,
        'search_path' => 'identity,public',
        'sslmode' => 'prefer',
    ],

    'students'   => [/* ... */ 'search_path' => 'students,public'],
    'scheduling' => [/* ... */ 'search_path' => 'scheduling,public'],
    'care'       => [/* ... */ 'search_path' => 'care,public'],
    'billing'    => [/* ... */ 'search_path' => 'billing,public'],
    'documents'  => [/* ... */ 'search_path' => 'documents,public'],
    'notifications' => [/* ... */ 'search_path' => 'notifications,public'],
    'reporting'  => [/* ... */ 'search_path' => 'reporting,public'],
],
```

### 3.3 Por qué `search_path` y no nombres cualificados

> [!danger] Gotcha G3 — `hasTable()` falla con nombres cualificados
> Laravel's `Schema::hasTable('identity.users')` **no funciona** de forma fiable con
> `search_path` porque el método consulta `information_schema` con el nombre completo.
>
> **Solución adoptada:** cada modelo declara su conexión, y las migraciones usan
> `Schema::connection('identity')->hasTable('users')` — nombre **sin** schema, con la
> conexión estableciendo el `search_path`.

```php
// packages/identity/database/migrations/..._create_users_table.php
public function up(): void
{
    Schema::connection('identity')->hasTable('users');  // ✅ funciona
}
```

**El `search_path` evita:**
- Repetir el schema en cada nombre de tabla.
- Errores de typos en el nombre del schema.
- Inconsistencias entre migraciones y modelos.

**El `search_path` impone:**
- No se pueden referenciar tablas de otro schema con el nombre corto.
- Las FKs cross-schema deben escribirse explícitas: `REFERENCES students.students(id)`.

### 3.4 FKs cross-schema

Solo se permiten hacia dos schemas:

```sql
-- ✅ Permitido: hacia students (referencias de alumnos)
ALTER TABLE care.clinical_notes
    ADD CONSTRAINT clinical_notes_student_id_fkey
    FOREIGN KEY (student_id) REFERENCES students.students(id) ON DELETE RESTRICT;

-- ✅ Permitido: hacia identity (usuarios)
ALTER TABLE care.clinical_notes
    ADD CONSTRAINT clinical_notes_author_user_id_fkey
    FOREIGN KEY (author_user_id) REFERENCES identity.users(id) ON DELETE RESTRICT;

-- ❌ Prohibido: de care hacia billing
-- (Y ni siquiera es necesario: no hay relación entre notas clínicas y pagos)
```

**Justificación:** el módulo `care` necesita saber **quién** es el alumno (para mostrar la
ficha) y **quién** escribió la nota. Eso no crea dependencia de negocio: son referencias
de identidad, no relaciones de dominio.

## 4. Rendimiento

### 4.1 Vacuum y autovacuum

Las tablas de auditoría crecen rápido. Configuración específica:

```sql
-- Tabla de auditoría: vacuum más agresivo
ALTER TABLE identity.audit_events SET (
    autovacuum_vacuum_scale_factor = 0.05,   -- Vacuum al 5% de crecimiento
    autovacuum_analyze_scale_factor = 0.02
);

-- Tabla de notas clínicas (el contenido cifrado infla el tamaño)
ALTER TABLE care.clinical_notes SET (
    autovacuum_vacuum_scale_factor = 0.1,
    toast.autovacuum_vacuum_scale_factor = 0.1
);
```

```sql
-- Verificar el estado de vacuum
SELECT
    schemaname, relname,
    n_live_tup, n_dead_tup,
    last_vacuum, last_autovacuum,
    round(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 2) AS dead_pct
FROM pg_stat_user_tables
WHERE n_dead_tup > 0
ORDER BY n_dead_tup DESC
LIMIT 20;
```

### 4.2 Una vacuum manual programada

```sql
-- /etc/cron.d/cai-vacuum  (no es necesario: autovacuum lo hace)
```

**Verificación de índices no utilizados:**

```sql
SELECT
    schemaname, relname, indexrelname,
    idx_scan, pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE schemaname NOT IN ('pg_catalog','information_schema')
ORDER BY idx_scan ASC
LIMIT 20;
```

Un índice con `idx_scan = 0` después de un mes de uso es un candidato a eliminarse.

### 4.4 `ANALYZE`

```sql
ANALYZE;   -- Actualiza las estadísticas del planificador
```

Se ejecuta semanalmente por cron si hay volumen alto. El autovacuum ya lo hace.

## 5. Conexiones desde Laravel

### 5.1 El patrón en los modelos

```php
// packages/billing/src/Models/Charge.php
declare(strict_types=1);

namespace Cai\Billing\Models;

use Illuminate\Database\Eloquent\Model;

final class Charge extends Model
{
    protected $connection = 'billing';      // ← obligatorio en cada modelo

    protected $table = 'charges';

    protected $fillable = [...];

    protected $casts = [
        'amount'         => 'decimal:2',
        'paid_amount'    => 'decimal:2',
        'due_date'       => 'date',
    ];
}
```

### 5.2 Transacciones

```php
// ✅ Correcto: la transacción se abre en la conexión del módulo
DB::connection('billing')->transaction(function () {
    // ...
});
```

> [!warning] La transacción y la auditoría
> La auditoría se escribe en la conexión `identity`. Si la operación de negocio está en
> `billing` y la auditoría en `identity`, **no comparten transacción** salvo que ambas
> apunten a la misma base de datos física (que es el caso: una sola base `cai`).
>
> En PostgreSQL, dos conexiones distintas **a la misma base de datos** sí pueden
> participar de la misma transacción **si se usa `SET LOCAL` y se mantiene la misma sesión**.
> Laravel no lo hace automáticamente. **Solución en el MVP:** el helper de auditoría abre
> la transacción en la conexión del módulo y escribe el evento con esa misma conexión
> (`DB::connection($module)->table('...')` con el schema explícito).
>
> Verificar en F2 con un test de fallo en cascada.

### 5.3 La auditoría con schema explícito

```php
// packages/core/src/Audit/Auditor.php
public function record(string $action, string $entityType, mixed $entityId, array $options = []): void
{
    $connection = DB::connection($options['connection'] ?? 'identity');

    $connection->table('identity.audit_events')->insert([
        'actor_user_id' => Auth::id(),
        'action'        => $action,
        'entity_type'   => $entityType,
        'entity_id'     => (string) $entityId,
        'student_id'    => $options['student_id'] ?? null,
        'changes'       => $options['changes'] ?? null ? json_encode($options['changes']) : null,
        'context'       => $options['context'] ?? null ? json_encode($options['context']) : null,
        'ip_address'    => request()?->ip(),
        'user_agent'    => Str::limit((string) request()?->userAgent(), 255),
        'created_at'    => now(),
    ]);
}
```

## 6. Seguridad de la base de datos

### 6.1 `pg_hba.conf` estricto

```ini
# TYPE  DATABASE  USER  ADDRESS         METHOD
local   all       all                   peer
host    all       all   127.0.0.1/32    scram-sha-256
host    all       all   ::1/128         scram-sha-256
```

> [!danger] Nunca `0.0.0.0/0`
> Si el servidor va a estar en la LAN del centro, se puede agregar una entrada
> **específica** para el segmento de la LAN con el rol adecuado. Lo seguro es dejarlo en
> `localhost` y acceder por la aplicación.

### 6.2 Contraseñas

```sql
ALTER ROLE cai WITH PASSWORD 'CAMBIAR_ESTA_CLAVE';
```

- Contraseña de **16+ caracteres**, generada.
- Se guarda en el gestor de contraseñas.
- Se cambia cada 6 meses o ante cualquier sospecha.

## 7. Monitoreo de la base

```sql
-- Conexiones activas
SELECT
    datname, usename, state, count(*),
    max(now() - query_start) AS longest_query
FROM pg_stat_activity
WHERE datname = 'cai'
GROUP BY 1, 2, 3
ORDER BY 4 DESC;

-- Consultas más lentas (requiere pg_stat_statements)
SELECT
    round(mean_exec_time, 2) AS ms_medio,
    calls,
    left(query, 100) AS consulta
FROM pg_stat_statements
ORDER BY mean_exec_time DESC
LIMIT 10;

-- Cache hit ratio (debe ser > 99%)
SELECT
    sum(heap_blks_hit) / NULLIF(sum(heap_blks_hit) + sum(heap_blks_read), 0) * 100
        AS cache_hit_ratio
FROM pg_statio_user_tables;

-- Tamaño de las bases
SELECT
    pg_database_size(datname) AS tamano,
    pg_size_pretty(pg_database_size(datname)) AS legible
FROM pg_database
WHERE datname LIKE 'cai%';
```

| Métrica | Umbral | Acción |
|---|---|---|
| Cache hit ratio | < 99% | Revisar `shared_buffers` |
| Conexiones activas | > 80 | Revisar `pm.max_children` y las conexiones por request |
| Dead tuples | > 20% de las filas | Revisar autovacuum |
| Tamaño de la base | > 20 GB | Evaluar `VACUUM FULL` o particionado (fase 2) |
| Consultas > 1 s | Cualquiera | Optimizar |

## 8. Extensiones de PostgreSQL

| Extensión | ¿Se usa? | Para qué |
|---|---|---|
| `pgcrypto` | ⚠️ Opcional | Hashing de contraseña (no necesario; usa `bcrypt` de Laravel), UUID |
| `uuid-ossp` | ❌ No | Se usa `bigint` autoincremental |
| `pg_trgm` | ⚠️ Opcional (F8) | Búsqueda difusa de nombres para autocompletado |
| `btree_gin` | ❌ No | No hay índices GIN |
| `unaccent` | ❌ No | La búsqueda no ignora acentos (decisión: buscar "Gonzalez" **sí** encuentra "González" con el índice español) |

```sql
-- Activar (si se decide usar)
CREATE EXTENSION IF NOT EXISTS pg_trgm WITH SCHEMA public;
```

> [!note] `pg_trgm` para la búsqueda de alumnos
> El autocompletado de alumnos por nombre es cómodo. En F8 se evalúa activarla. No es
> necesaria para el MVP.

```cron
# /etc/cron.d/cai-postgres
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/sbin:/bin:/usr/sbin:/usr/bin

# Estadísticas diario a las 03:30 (después del backup de las 23:00)
30 3 * * * postgres psql -d cai -c "ANALYZE;" >> /var/log/cai-pg.log 2>&1

# Logrotate de los logs de PostgreSQL
```

```bash
# Configurar logrotate
sudo cat > /etc/logrotate.d/postgresql <<'EOF'
/var/log/postgresql/*.log {
    weekly
    rotate 8
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
    su postgres adm
}
EOF
```

- [ ] El rol `cai` **no** puede borrar auditoría
