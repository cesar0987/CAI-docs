# Plan maestro de implementación — Sistema Integral de Gestión del Centro de Atención Inclusiva (CAI)

**Versión del plan:** 1.0
**Fecha:** 22 de octubre de 2026
**Estado:** vigente · las definiciones que faltan de Dirección están en [[01.07 Preguntas Abiertas y Decisiones Pendientes]]
**Documento complementario:** [[ARQUITECTURA-SISTEMA-CAI (v1 - documento original)]] (antecedente: arquitectura funcional y de datos)

> Este documento es el **plan de ejecución**. Cubre el análisis previo, las decisiones
> estructurales, el protocolo de versionado/rollback, los roles y el paso a paso de
> implementación. El documento de arquitectura define **qué** se construye; este define
> **cómo se construye sin que se rompa**.

## 0. Resumen de decisiones tomadas

| # | Decisión | Elección | Consecuencia principal |
|---|---|---|---|
| D1 | Repositorio y CI | **GitHub privado + GitHub Actions** | CI obligatoria: ninguna migración llega a `main` sin tests verdes |
| D2 | Modularidad | **Paquetes Composer por dominio** (`packages/*`) | Las fronteras las impone el autoload, no la disciplina del dev |
| D3 | Aislamiento de datos | **Un schema PostgreSQL por módulo** | Un módulo no puede tocar tablas de otro; dumps y extracción por módulo |
| D4 | Despliegue | **Script de release + symlink `current`** | Rollback de código en segundos, sin redeploy |
| D5 | Equipo | **1 desarrollador, tiempo parcial** | Priorizar pocas piezas, cero infraestructura que mantener de más |
| D6 | Stack | Laravel (versión vigente compatible con Filament) + Filament + PostgreSQL 16 | Sin Next.js en el MVP |
| D7 | Modelo de cobro | **Cuenta familiar compartida** | `family_accounts` + `family_account_members` con historial |
| D8 | Seguimiento | **Registros clínicos/terapéuticos detallados** | Área `care` con cifrado de aplicación y permisos propios |
| D9 | Alojamiento | **Servidor propio en el centro** | Backups externos cifrados, VPN, UPS |
| D10 | Portal familiar | **Segunda etapa** | La lógica de negocio vive en paquetes, no en Filament, para poder reutilizarla |

### Corrección que este plan introduce sobre el documento de arquitectura

`docs/ARQUITECTURA-SISTEMA-CAI.md` §7 define un **"monolito modular"** con carpetas en
`app/Domain/`. Eso es modularidad **nominal**: las fronteras existen solo por convención y
se rompen con el primer `use App\Models\OtherModel` de un `use` rápido.

Este plan lo reemplaza por **modularidad estructural y verificable**:

- **Paquetes Composer** → el autoload hace imposible el acceso directo entre módulos.
- **Contracts + eventos** → única vía de comunicación entre módulos.
- **Deptrac + arch tests** → la CI falla si alguien rompe una frontera.
- **Schemas separados en PostgreSQL** → el motor de base de datos también aísla.

> **Acción pendiente post-aprobación:** actualizar §7 de `docs/ARQUITECTURA-SISTEMA-CAI.md`
> para que refleje la estructura de paquetes. No se hace hasta que apruebes este plan.

## 2. Iteración 1 — Alcance real, carga y dimensionamiento

### 2.1 Qué se pidió y qué se necesita realmente

Pedido: sistema integral para ~300 alumnos, 20–50 usuarios, atención mixta, finanzas
completas, portal familiar en etapa 2, servidor propio, modular y con versionado que
permita volver atrás sin romper.

### 2.2 Carga estimada con números concretos

| Recurso | Cálculo | Volumen |
|---|---|---|
| Alumnos | 300 hoy → 600–800 en 3 años | Bajo |
| Familias/cuentas | ~180–250 (hermanos comparten) | Bajo |
| Sesiones | 300 alumnos × ~4 sesiones/semana × 45 semanas ≈ **54.000 sesiones/año** | Medio |
| Registros de asistencia | ≈ 54.000–120.000/año (grupales multiplican) | Medio |
| Notas clínicas | ~2–6 por alumno/mes ≈ 5.000–20.000/año | Medio |
| Cargos mensuales | 300 alumnos × 12 ≈ **3.600/año** | Bajo |
| Pagos | ~1.500–3.500/año | Bajo |
| Usuarios concurrentes | 20–50 usuarios, **pico real 5–10 simultáneos** | Muy bajo |
| Transacciones concurrentes de escritura | < 20/s en pico | Muy bajo |

### 2.3 Conclusión de la iteración

El volumen **no justifica** microservicios, ni CQRS, ni event sourcing, ni Kubernetes, ni
Redis, ni Read replicas. Un monolito modular sobre una sola máquina virtual de 4 vCPU / 8 GB
(PostgreSQL incluido) maneja esto con margen de 10×.

**Pero** el volumen **sí justifica** invertir en:

- Modularidad real → porque el sistema vivirá 5+ años y
  diferentes personas lo tocarán..
- Versionado y rollback → porque habrá cambios frecuentes sobre un sistema que **no puede
  caerse**: si el centro no puede registrar la asistencia de hoy, la operación se detiene.
- Aislamiento de datos clínicos → porque es un requisito legal y ethical, no técnico.

> **Regla de la iteración 1:** la complejidad se paga **en los límites**, no en la
> infraestructura. Cada pieza extra (servicio, cola, caché) es un componente que puede
> caerse a las 3 de la mañana. El presupuesto de piezas: **1 servidor, 1 base de datos,
> 1 aplicación, 1 proceso de cola opcional**.

## 3. Iteración 2 — Riesgos críticos y puntos de falla

Ordenados por probabilidad × impacto. El Top 5 condiciona el diseño.

### R1 — Un cambio rompe otra parte del sistema *(prob. alta, impacto alto)*

**Escenario:** se agrega un campo a `students`; un `use App\Models\Student` en `billing`
falla; el panel de finanzas queda en blanco.

**Mitigaciones en cascada:**
1. Paquetes Composer → el acceso directo es imposible de compilar (§8.3).
2. Contracts → toda comunicación pasa por interfaces.
3. Deptrac + arch tests → la CI falla antes del merge.
4. `expand–contract` → el schema nunca queda incompatible con un release anterior.
5. Feature flags → se puede apagar un módulo sin redesplegar.

### R2 — Migración destructiva en producción y no hay vuelta atrás *(prob. media, impacto muy alto)*

**Escenario:** `DROP COLUMN` o un `NOT NULL` sobre datos que ya importó el centro.

**Mitigación:** migraciones inmutables + `expand–contract` + backup `pg_dump` previo a
**cada** release + política explícita de que **jamás** se hace rollback de DB automática.

### R3 — Filtración de datos clínicos a personal no autorizado *(prob. media, impacto muy alto/legal)*

**Escenario:** un widget general, una exportación o una búsqueda global expone notas
terapéuticas a recepción o a administración.

**Mitigación:** separación de área `care` con schema propio, cifrado de contenido, permisos
por *record* y no solo por rol, prohibición de notas clínicas en exportaciones, y
auditoría de cada lectura sensible (`audit_events` / `security_events`).

### R4 — Dependencia de una sola persona *(prob. certeza, impacto alto)*

**Escenario:** el único dev no puede trabajar 2 semanas; el centro queda sin soporte y sin
poder corregir nada.

**Mitigación:** documentar todo en el repo (`docs/`), README por paquete, ADRs
(Architecture Decision Records) para las decisiones no obvias, backups del repo (GitHub),
y un **runbook de operaciones** escrito para alguien no técnico.

### R5 — Servidor propio: hardware, energía o robo *(prob. media, impacto muy alto)*

**Escenario:** disco duro del servidor falla o se roba el equipo → pérdida total.

**Mitigación:** UPS, RAID o mejor, **backup externo cifrado fuera del edificio**, verificación
mensual de restauración, y documentado explícitamente: **un backup en el mismo servidor no
es un backup**.

### Riesgos secundarios

| # | Riesgo | Mitigación |
|---|---|---|
| R6 | Datos de planilla actual sucios o duplicados | Importador con validación y reporte de rechazos; nunca se pisa la BD de producción durante la carga |
| R7 | Números de teléfono/celular con formatos heterogéneos | Columna `string` + normalización opcional; **no** usar `numeric` para teléfonos |
| R8 | Zona horaria y horarios de sesión mal interpretados | `TIMESTAMPTZ` en DB, `APP_TIMEZONE` fijo, nunca `timestamp` sin tz |
| R9 | Cálculo de cuotas con redondeos | `NUMERIC(14,2)` + `bcmath` + cast `decimal`; nunca `float` |
| R10 | Falta de espacio de trabajo wiped por una migración fallida | Todo en transacción (`migrate` usa transacciones en PostgreSQL) + `down()` probado |
| R11 | El centro cambia el proceso de cobro a mitad del proyecto | Reglas de negocio documentadas y versionadas (§11 F2) antes de codificar |
| R12 | Puertos abiertos y PostgreSQL expuesto | `postgresql.conf` con `listen_addresses = 'localhost'`, firewall, fail2ban en SSH |

## 4. Iteración 3 — Modularidad real: del "monolito modular" nominal al modular verificable

### 4.1 Tres niveles de modularidad, y por qué el actual es insuficiente

| Nivel | Cómo se aplica | Frontera garantizada por | Costo |
|---|---|---|---|
| **N0 — Carpetas** | `app/Domain/Students/...` | Nada. Convención. | Bajo |
| **N1 — Namespaces** | `App\Domain\Students\...` + PSR-4 | Nada. Convención. | Bajo |
| **N2 — Paquetes + contratos + CI** | `packages/students` con `composer.json` propio | **El autoload y la CI** | Medio |
| **N3 — Servicios separados** | Microservicios | La red | Alto |

**Se elige N2.** Es el punto donde la modularidad deja de depender de que "me acuerde de no
importar el modelo de otro módulo" y empieza a ser una restricción del sistema de archivos.

### 4.2 Por qué N2 y no N3 (microservicios)

| Criterio | N2 (paquetes) | N3 (microservicios) |
|---|---|---|
| Transacción ACID entre módulos | **Posible** (misma DB) | Imposible sin saga/distribuido transaccional |
| Coste operativo | 1 despliegue | 6+ despliegues, orquestación, observabilidad distribuida |
| Latencia | Nativa | Red (y el servidor del centro tiene una sola IP) |
| Debugging | Un stack trace | 5 servicios, 5 logs, correlación de IDs |
| Apto para 1 dev part-time | **Sí** | No |
| Escalabilidad independiente | No (no la necesita) | Sí (no la necesita) |

**Conclusión:** con 300 alumnos, 5–10 usuarios concurrentes y 1 desarrollador part-time, los
microservicios son un costo sin retorno. La modularidad que aporta N2 (acoplamiento bajo,
cambios acotados) se consigue sin el costo operativo.

### 4.3 Por qué no N0/N1 (la estructura del documento actual)

Con N0/N1:
- `use App\Models\Student` desde `billing` compila, funciona y **no falla ningún test**
  porque no hay ninguna regla que lo prohíba.
- El acoplamiento se descubre cuando falla en producción, no en desarrollo.
- "Modular" queda en un documento que nadie aplica.

Con N2:
- `billing` **no puede** resolver `App\Models\Student`: la clase no existe en su autoload.
- La única forma de obtener datos de alumnos es `students\Contracts\StudentDirectory`.
- Si ese contrato cambia, la CI detecta quién lo usa y el cambio queda acotado.

### 4.4 Las 4 reglas de frontera (normativa, verificable por CI)

> **R1 — Propiedad de sus datos.** Cada módulo es dueño de sus tablas y de su schema.
> Ningún otro módulo escribe en ellos. Las FKs cross-schema son la **única** excepción
> permitida (y solo hacia entidades de identidad/alumnos), por integridad del historial.

> **R2 — Comunicación por contrato.** Un módulo A necesita datos de B → B expone una
> interfaz en `B/Contracts/` y una implementación en `B/Providers/`. A consume **solo**
> la interfaz. A nunca importa el modelo Eloquent de B.

> **R3 — Comunicación por evento.** Un módulo A notifica un cambio → emite un evento de
> dominio con payload plano (DTOs, sin modelos Eloquent, sin datos clínicos) en
> `A/Events/`. B lo escucha en `B/Listeners/`. Sin acoplamiento temporal, sin dependencias
> circulares.

> **R4 — Sin relaciones Eloquent cross-módulo.** `belongsTo`/`hasMany` solo dentro del
> propio módulo. Entre módulos: FK por ID (o por contrato). Razón: una relación Eloquent
> cross-módulo crea un acoplamiento invisible en el modelo y hace que un cambio de clave
> en B rompa A en runtime.

### 4.5 Capas dentro de cada paquete

```
packages/<módulo>/
  src/
    Contracts/       ← interfaces públicas que este módulo EXPONE (R2)
    Events/          ← eventos que este módulo EMITE (R3)
    Listeners/       ← eventos de otros que este módulo ESCUCHA
    Actions/         ← casos de uso (una intención de negocio = una Action)
    Services/        ← lógica de dominio reutilizable entre Actions
    Models/          ← Eloquent. Privados del módulo.
    Policies/        ← autorización por registro
    Observers/       ← hooks de modelo
    Jobs/            ← procesos en background
    Filament/        ← recursos de panel (capa de presentación)
    DTOs/            ← objetos de transferencia
    Enums/           ← enums PHP 8.1+
    Exceptions/      ← errores de dominio
    Providers/       ← service provider del módulo
```

**Regla de dependencia interna:** `Filament` → `Actions` → `Services` → `Models`.
Nunca al revés. El panel es *un cliente* del dominio, no su dueño. Esto es lo que permite
que el portal familiar del futuro sea **otro cliente** de las mismas Actions.

### 4.6 Efecto sobre el versionado

La modularidad + contratos habilitan el versionado semántico **por paquete**:

- `cai/students: v1.2.0` — el contrato `StudentDirectory` cambió de forma compatible → `^1.2`.
- `cai/students: v2.0.0` — cambió incompatible → los que dependan deben actualizarse.
- Un módulo puede **deprecarse** (`cai/reporting: v1.0.0, deprecated`) sin romper a nadie.

Esto es lo que hace que "cambiar cosas no rompa el sistema" sea una propiedad estructural y
no una esperanza.

## 5. Iteración 4 — Versionado y rollback: la garantía real de "no romper"

### 5.1 La pregunta correcta

> «Si mañana subo un cambio y el centro llama a las 20:00 diciendo que no puede registrar
> asistencia, ¿cuánto tarda el sistema en volver a estar operativo y con los datos
> intactos?»

La respuesta debe estar **por escrito, medida y ensayada**. Ese es el objetivo de diseño.

### 5.2 Las 4 capas que dan esa garantía

| Capa | Qué protege | Cuándo se activa |
|---|---|---|
| **1. Frontera modular** | Un cambio no rompe otros módulos | Siempre, en CI |
| **2. Expand–contract** | El schema siempre es compatible con el release anterior | Siempre, en migraciones |
| **3. Feature flags** | Una funcionalidad se apaga sin redesplegar | Cuando algo falla en prod |
| **4. Backups + release con symlink** | Se vuelve a un estado anterior con datos intactos | Último recurso |

### 5.3 Expand–Contract en detalle (el mecanismo central)

Toda migración que pueda romper un release anterior se divide en **3 deploys**:

```
DEPLOY 1 — EXPAND      (seguro, retrocompatible)
  ADD COLUMN discharge_reason TEXT NULL
  → El código viejo no la conoce. No le afecta. Sigue funcionando.
  → Se hace el deploy.

DEPLOY 2 — MIGRATE    (dual-write + backfill)
  Código nuevo escribe en la columna nueva Y en la vieja.
  Un job por lotes rellena la nueva para los registros existentes.
  → Ambas versiones de código leen lo mismo.
  → Se hace el deploy.

DEPLOY 3 — CONTRACT   (retirada)
  El código usa solo la columna nueva.
  DROP COLUMN discharge_reason  ← recién acá
  → Ya no se necesita volver atrás: el release anterior ya no es soportado.
```

**Invariante que se puede auditar:** *en todo momento, la versión anterior del código sigue
funcionando con el schema actual.* Eso es lo que convierte un rollback de código en una
operación de 30 segundos en lugar de una restauración de base de datos.

**Checklist de migración — obligatorio en cada PR:**
- [ ] ¿Es reversible (`down()`)? Si no, ¿es parte de un expand–contract y está documentado?
- [ ] ¿Es compatible con el código del release anterior?
- [ ] ¿Toca datos de más de X filas? → backfill por lotes, no en la migración.
- [ ] ¿Hay que esperar a que el backfill termine antes del deploy 3? → sí, gate explícito.
- [ ] ¿Hay que pausar escrituras durante la migración? → solo en casos excepcionales.

### 5.4 Matriz de rollback (de más rápido a más profundo)

| Nivel | Mecanismo | Tiempo | Recovered | Cuándo usarlo |
|---|---|---|---|---|
| **1. Kill switch** | Feature flag `module.billing.enabled = false` | **Segundos** | Total del módulo | Bug en una funcionalidad, sin corrupción de datos |
| **2. Rollback de código** | `ln -sfn releases/<anterior> current` + `optimize:clear` | **~1 minuto** | Total, sin pérdida de datos | Bug introducido en el release actual; el schema no cambió incompatiblemente (expand–contract lo garantiza) |
| **3. Rollback de código + DB** | Restaurar `pg_dump` previo al release | 30–90 min | **Pierde los datos escritos después del backup** | Migración que corrompió datos a pesar de las reglas |
| **4. Disaster recovery** | Restaurar backup externo cifrado + `APP_KEY` | Horas | Según el último backup | Pérdida del servidor / ransomware / corrupción masiva |

**Regla operativa:** los niveles 1 y 2 son **rutina**. El nivel 3 requiere **decisión
explícita** y ventana declarada. El nivel 4 es un **desastre**, y para eso existe el
procedimiento escrito.

### 5.5 Lo que NUNCA se hace

- ❌ `migrate:rollback` en producción como mecanismo de rollback.
- ❌ Editar una migración que ya corrió en un entorno compartido.
- ❌ `git push --force` a `main` o a tags.
- ❌ Cambiar una migración aplicada en producción en lugar de crear una nueva.
- ❌ Desplegar sin backup previo verificado.
- ❌ Migraciones que reescriben masivamente datos dentro del `up()`.

### 5.6 Backups (relación directa con el rollback)

| Tipo | Cuándo | Retención | Dónde | Verificación |
|---|---|---|---|---|
| Pre-release `pg_dump` | Antes de cada deploy | 5 últimos | Servidor | Automática (el script falla si no se genera) |
| Diario cifrado | Automático 02:00 | 7 diarios + 4 semanales + 3 mensuales | Servidor | Automática |
| **Externo cifrado** | Copia del diario |Igual | **Fuera del edificio** (nube cifrada o disco en otra sede) | Mensual: restore en DB aislada |
| Documentos privados | Junto con la DB | Igual | Disco externo + nube cifrada | Mensual |
| **Claves (`APP_KEY`, claves de cifrado)** | Al crear / rotar | Permanente | **Gestor de contraseñas, no en el backup del server** | Trimestral |

> Un backup sin su clave es un backup inservible. Y un backup en el mismo servidor no es un
> backup.

**Objetivos de recuperación (a medir, no a suponer):**
- **RPO ≤ 1 h** con archivado de WAL (`pgBackRest` o `barman`) → PITR.
- **RTO ≤ 4 h** para restaurar el servicio completo en el servidor del centro.

### 5.7 Release y rollback como scripts (no como pasos manuales)

```
bin/cai release deploy      # construye release desde un tag, migra, cambia symlink, health check
bin/cai release rollback    # vuelve al release anterior (nivel 2)
bin/cai release status      # release actual, migraciones aplicadas, estado de la DB
bin/cai backup verify      # restaura el último backup en una DB aislada y valida
bin/cai module:enable billing   # kill switch por módulo
```

Cada release vive en `releases/<fecha>-<versión>/` y `current` es un symlink. Se conservan
las últimas 5 releases en disco; el código completo se conserva 90 días vía el backup del
repositorio.

## 6. Iteración 5 — Proceso, roles, capacidad operativa y auto-crítica

### 6.1 Proceso de trabajo

- **Trunk-based.** `main` siempre desplegable y verde. Ramas cortas (`feature/...`,
  `fix/...`), vida < 3 días. **No** existe `develop` permanente.
- **PR obligatorio** con CI verde. Aunque seas el único dev, el PR es tu revisión: la
  checklist del PR es tu segundo par de ojos.
- **Commits convencionales** → `release-please` genera CHANGELOG y tags automáticamente.
- **Una entrega = un PR = un tag.** No se mezclan refactors grandes con features.

### 6.2 Autocrítica del plan (qué podría estar mal)

| Preocupación | Veredicto | Mitigación |
|---|---|---|
| ¿6 paquetes es demasiado para 1 dev part-time? | **Riesgo real.** La sobrecarga de mover código entre paquetes puede superar el beneficio. | Los paquetes nacen pequeños (1 archivo, 1 interface). La ceremonia solo crece si el módulo crece. Regla: **no crear un paquete hasta que el módulo tenga ≥ 3 clases y un consumidor real.** |
| ¿Deptrac + arch tests + release-please + expand–contract es demasiado tooling? | 4 herramientas nuevas. | Se incorporan **una por fase**, cada una justificada por un fallo real que ya ocurrió, no preventivamente. Prioridad: Deptrac (F1) → expand–contract como práctica (F2) → feature flags (F6) → release-please (F8). |
| ¿Feature flags sin un panel de configuración? | Flags dispersos en `.env` = imposible de auditar. | `identity.feature_flags` en DB + panel Filament en `F6`, con quién/cuéndo/cambió. |
| ¿El schema por módulo complica Laravel? | **Sí, hay gotchas reales** (ver §8.5). | Documentadas con workarounds desde el día 1. Si en la práctica molestan más de lo que aportan, la alternativa es un solo schema con prefijos — decisión reversible porque las migraciones son jóvenes y se rehacen con facilidad. |
| ¿Y si el centro pide funciones que rompen la modularidad? | "Necesito un listado de alumnos con saldo y notas en una sola pantalla" | Eso es un **módulo de lectura (`reporting`)** que consume contratos. Es una necesidad legítima, no una violación. |
| ¿Qué pasa si el proyecto se estanca 3 meses? | **Escenario más probable.** | Cada paquete tiene un README y un ADRs actualizado. `main` siempre desplegable → retomar es clonar + composer install. |
| ¿Y si el dev deja de estar disponible? | Bus factor = 1. | Runbook de operaciones, ADRs, docs/ en el repo, y un checklist de "handoff" al final de cada fase. |

### 6.3 Hitos de "listo para producción" por fase

Cada fase termina con un **gate** verificable. No se avanza sin cumplirlo.

## 7. Comparaciones

### 7.1 Sistemas de referencia: qué mirar y qué copiar

| Sistema | Dominio | Qué copiar | Qué NO copiar |
|---|---|---|---|
| **ERPNext** | Salud, educación, ONG | Separación estricta por dominio (Health, Education); tipos de documento por dominio; roles granulares; reportes por periodo | Framework y ORM propios; UI; localización (el centro opera en PYG, ERPNext calcula en INR) |
| **Odoo** | ERP general | **Reglas de acceso por registro** (`record rules`), no solo por rol — un profesional solo ve *sus* alumnos | ORM genérico (`ir.model`); mercado de complementos (addons); capa JS |
| **OpenEMR / OpenMRS** | Salud | Separación estricta entre **datos clínicos** y **administrativos/financieros**; auditoría granular de acceso; el "encounter" ≈ nuestra **sesión**; `consent` como entidad | Complejidad FHIR/ICD; interoperabilidad; encriptado overkill |
| **Moodle** | Educación | Separación curso / matrícula / actividad; el contenido pertenece a un módulo; plugins como unidad de extensión | Sistema de plugins de terceros |
| **Care2go / Care Manager** (servicios de desarrollo) | Atención a discapacidad | **Vocabulario de dominio**: plan de servicio, objetivo, progreso, unidad de servicio (hora) facturable, autorización de horas, informes de progreso | Su modelo de datos y su antigüedad |

| **Home Assistant / n8n** | Orquestación | *No aplica.* Ninguna dependencia de automatización externa en el MVP | Automatizaciones que el centro no pidió |

**Síntesis de la comparación:** el patrón que se repite en todos los sistemas maduros es el
mismo — **dominios con datos propios, comunicación por contrato/evento, control de acceso por
registro, y auditoría de lo sensible**. Eso es exactamente lo que este plan formaliza.

### 7.2 Enfoques de arquitectura

| Enfoque | Modularidad | Transacciones | Costo op. | Estado de los datos | Veredicto |
|---|---|---|---|---|---|
| Monolito por capas (`Http/ → Service/ → Model/`) | Ninguna | Sí | 1 | Un schema | ❌ Descartado |
| Monolito modular en carpetas | Nominal | Sí | 1 | Un schema | ⚠️ Insuficiente |
| **Monolito modular en paquetes + schemas** | **Estructural, verificada por CI** | **Sí** | **1** | **Un schema por módulo** | ✅ **Elegido** |
| `spatie/laravel-modules` | Media | Sí | 1 | Un schema | ⚠️ Alternativa: menos control sobre el versionado por paquete y contratos |
| Hexagonal / Clean Architecture estricta | Alta | Sí | 1 | Un schema | ⚠️ Correcta pero costosa en ceremonia para 1 dev part-time |
| Microservicios | Máxima | No (sin saga) | 6+ | 6 DB | ❌ Descartado |
| Event sourcing | N/A | N/A | Alta | 1 DB | ❌ Descartado (no hay requerimiento de auditoría temporal exhaustiva) |

### 7.3 Estrategias de versionado de código

| Estrategia | Ramas | Merge | Adecuado para | Veredicto |
|---|---|---|---|---|
| **Git Flow** | `develop` + `release` + `hotfix` | Lento, conflictos frecuentes | Equipos grandes con releases programados | ❌ Demasiado ceremonia |
| **GitHub Flow** | `main` + PR | Continuo, deploy por PR | Equipos pequeños | ⚠️ Base |
| **Trunk-based + tags + feature flags** | `main` + ramas cortas | Continuo | Requisito: poder apagar sin redesplegar | ✅ **Elegido** |

**Complemento automático:** `release-please` → Conventional Commits → CHANGELOG + tags
SemVer, con soporte de **monorepo** (bumpea la versión de cada paquete según qué cambió en
su path). Es lo que hace que el versionado no dependa de que uno se acuerde de subir el
número.

### 7.4 Esquema y migraciones

| Herramienta | Ajuste al stack | Veredicto |
|---|---|---|
| **Laravel Migrations nativas** | Ninguno; integrado con `migrate`, `rollback`, testing | ✅ **Elegido** |
| Liquibase / Flyway | Java/otro runtime; hubiera que mantener dos | ❌ |
| Atlas (ariga) | Declarativo, diffing declarativo → útil con varios devs; pero agrega un motor y un formato extra | ⚠️ Revisar si el equipo crece |
| Schema diffing automático desde modelos | Verdbcado: el schema es la fuente de verdad, no el código | ❌ Peligroso con migración y datos |

### 7.5 Verificación automática

| Herramienta | Para qué | Costo | Veredicto |
|---|---|---|---|
| **Pest** | Tests legibles (sintaxis de test unitario) + **arch tests** (`expect()` sobre capas) | Bajo | ✅ Elegido |
| PHPUnit | Alternativa estándar, más verbosa | Bajo | ⚠️ Fallback |
| **Deptrac** (con `deptrac-laravel`) | Detecta violaciones de capa y de módulo | Bajo | ✅ Elegido en F1 |
| Larastan / Larastan + PHPStan | Análisis estático, tipos, Nullable safety | Medio | ✅ En F1 (nivel 5) |
| Rector | Refactoring automático con reglas | Medio | ⚠️ En F4+, si hay deuda acumulada |
| Infection (mutation testing) | Calidad real de los tests | Alto | ❌ No en el MVP |

### 7.6 Comparación de la decisión "modular" contra un monolito simple

| Aspecto | Monolito simple | Monolito modular en paquetes |
|---|---|---|
| Velocidad del primer mes | ✅ Mayor | ⚠️ Menor (estructura) |
| Velocidad del mes 12 | ⚠️ Decrece (acoplamiento) | ✅ Se mantiene |
| Cambiar un módulo | ❌ Riesgo de romper otros | ✅ Acotado |
| Reutilizar lógica en el portal familiar | ⚠️ Extraer después es caro | ✅ Ya está lista |
| Incorporar otro dev (o que te contracten) | ❌ Difícil | ✅ Onboarding por paquete |
| Onboarding de un nuevo dev (o que te contracten) | ❌ Hay que entender todo | ✅ Hay que entender lo que toca |
| Costo de la disciplina | — | ⚠️ Hay que aplicar las reglas |

**Veredicto:** el costo se paga una vez (setup de estructura) y se cobra cada vez que se
cambia algo. Como este sistema va a vivir 5+ años y cambiará 3 veces por semana
durante los primeros 2 años, la inversión se paga sola.

**Conexiones:** una conexión PostgreSQL por módulo, cada una con su propio `search_path`.

```php
// config/database.php (fragmento)
'students' => [
    'driver' => 'pgsql',
    'host' => env('DB_HOST', '127.0.0.1'),
    'port' => env('DB_PORT', '5432'),
    'database' => env('DB_DATABASE', 'cai'),
    'username' => env('DB_USERNAME', 'cai'),
    'password' => env('DB_PASSWORD'),
    'charset' => 'utf8',
    'prefix' => '',
    'search_path' => 'students, public',
    'search_path_setting' => true,
],
```

Cada modelo declara su conexión: `protected $connection = 'students';`

**Ventajas concretas:**
- `billing` **no puede** referenciar `students.students` sin cualificar explícitamente →
  aislamiento real, no de estilo.
- `pg_dump -n students` = backup del módulo en un archivo.
- Un módulo se puede **extraer** a otro sistema con un `pg_dump -n <schema>`.
- Las FKs cross-schema (`REFERENCES students.students(id)`) siguen siendo posibles para
  integridad del historial financiero.

**Trade-off asumido:** las transacciones **no cruzan módulos**. Esto es intencional: la
atomicidad crítica (cargo + pago + imputación + recibo) vive **dentro** de `billing`. La
comunicación entre módulos es por eventos `ShouldDispatchAfterCommit`, con listeners
idempotentes y reintentos (`failed_jobs`).

### 8.5 Gotchas conocidos de schemas en Laravel + PostgreSQL

Estos son los trampas reales. **Están documentados aquí para que no se descubran en
producción.**

| # | Gotcha | Síntoma | Workaround |
|---|---|---|---|
| G1 | `Schema::hasTable('students.students')` con nombre cualificado | `hasTable` busca en `current_schema()` con el nombre completo → devuelve `false` | Usar **conexiones con `search_path`** (no punto) → `hasTable('students')` funciona. |
| G2 | `migrate:fresh` sobre la conexión por defecto | `dropAllTables` solo ve `current_schemas()` → **no** borra los schemas de los módulos | Comando propio `bin/cai db:reset` que hace `DROP SCHEMA ... CASCADE` por módulo y vuelve a migrar |
| G3 | `Model::unguard()` / `preventLazyLoad` con `search_path` | Un modelo de `billing` que resuelva `students.students` por nombre corto falla en runtime | Tests que recolectan las queries ejecutadas y verifican el schema efectivo |
| G4 | `pg_dump` sin `-n` | Dump de todo, incluidos datos clínicos, en el mismo archivo | Dumpers separados por schema con cifrado por módulo → un backup de `billing` no expone notas clínicas |
| G5 | `Model::observe` + `SoftDeletes` con `search_path` | Sin impacto real; `search_path` aplica a todas las queries de la conexión | Ninguna |
| G6 | Orden de migraciones entre paquetes | El `timestamp` de archivo define el orden → colisiones si dos paquetes crean migraciones el mismo segundo | Prefijo de timestamp por paquete (`2026_01_01_000000_students_...`) + `migrate --path` por paquete en el orden documentado |
| G7 | `DB::transaction()` con eventos | Un evento dentro de la transacción puede leerse antes del commit | `ShouldDispatchAfterCommit` en todos los eventos de dominio |
| G8 | `pdo_pgsql` sin `bcmath` | Cast `decimal` de Laravel falla en runtime | Instalar `php8.3-bcmath` (ya identificado) |
| G9 | Collation distinto al esperado | `ORDER BY` de nombres con acentos inconsistentes | `COLLATE "C"` o `und-x-icu` fijo en el schema |

## 9. Roles

### 9.1 Roles de dominio (dentro del centro)

Son los roles de **usuario del sistema**. Se definen en `identity` y controlan el acceso a
Filament.

| Rol | Puede | No puede |
|---|---|---|
| **Dirección** | Indicadores generales; auditoría operativa; aprobar accesos excepcionales | Editar notas clínicas sin grant; ver datos clínicos en masa |
| **Secretaría** | Alumnos, tutores, matrículas, documentos administrativos, agenda | Notas clínicas; cuentas family's detalle de pagos |
| **Profesional** | Alumnos asignados; sus sesiones; asistencia; notas clínicas propias y de sus alumnos asignados; planes y objetivos de sus alumnos | Finanzas de la familia; alumnos no asignados; notas de otros profesionales (salvo grant) |
| **Coordinación** | Asignaciones; agenda; servicios; supervisión clínica **según competencia y grant**; planes de atención | Cobros y saldos (salvo que se le asigne) |
| **Finanzas** | Cuentas familiares, cargos, pagos, imputaciones, recibos, caja, reportes financieros | Notas clínicas; documentos clínicos; agendas de profesionales |
| **Recepción** | Agenda del día; datos de contacto mínimos; registrar autorización de retiro | Cualquier dato clínico; saldos históricos completos |
| **Administrador técnico** | Usuarios, roles, configuración, mantenimiento | Contenido clínico y financiero **ordinario** (salvo grant justificado y auditado) |

**Principio:** *el acceso al estado de cuenta no otorga acceso a la historia clínica del
alumno, y el acceso a la historia clínica no otorga acceso a la cuenta de la familia.*

### 9.2 Roles de desarrollo y operación (equipo técnico)

Siendo 1 dev part-time, estos roles se acumulan en una persona, pero **se documentan por
separado** para que el sistema pueda traspasarse.

| Rol | Responsabilidad | Quién (hoy) |
|---|---|---|
| **Dev Owner** | Escribe el código, hace las revisiones de sus propios PRs | yo |
| **Release Manager** | Decide qué entra en cada release, hace el deploy, verifica el health check | yo |
| **Incident Owner** | Responde a incidentes en producción; decide el nivel de rollback | yo (debe existir un contacto de respaldo del centro) |
| **Backup Custodian** | Verifica **semanalmente** que los backups existen y son restaurables; no desarrolla | **Debe ser alguien del centro**, no el dev (independencia de la verificación) |
| **Data Owner** (clínico) | Autoriza grants de acceso excepcional; aprueba la política de conservación | Dirección del centro + profesional responsable |

| **Product Owner** | Define qué entra y qué no en el MVP; valida con usuarios | Dirección del centro |

> **Riesgo a marcar:** *Backup Custodian ≠ Dev Owner*. Si el único dev verifica sus propios

> Designar a alguien del centro (p.ej. administración) con un checklist de 5 puntos.

Tareas:
1. Instalar extensiones faltantes: `sudo apt install php8.3-bcmath php8.3-gd`.
2. Verificar en `composer` qué versión de Laravel y Filament son compatibles entre sí
   (el plan **no fija** versiones hasta confirmarlo).
3. Instalar PostgreSQL server local (o usar el `docker-compose` v1 disponible) con
   `bcmath`/`sodium` disponibles en la extensión PHP.
4. Crear el repo local + remoto privado en GitHub con `main` protegida.
5. Escribir los **3 ADRs** que fijan lo decidido:
   - `ADR-0001-monolito-modular-en-paquetes.md`
   - `ADR-0002-schema-por-modulo.md`
   - `ADR-0003-expand-contract-y-feature-flags.md`
6. Escribir `docs/RUNBOOK.md` (borrador inicial) con los comandos de operación.

**Gate:** repo creado, `main` protegida, ADRs escritos, `bcmath` instalado, versiones
verificadas y anotadas.

**Se pospone:** todo lo demás.

### F1 — Andamiaje técnico + frontera modular

**Objetivo:** que la CI sea verde con el esqueleto de módulos y la frontera verificable.

Tareas:
1. `composer create-project laravel/laravel` en el repo (o `laravel new`).
2. Instalar Filament, Pest, Deptrac, Larastan, Pint, `spatie/laravel-permission`.
3. Crear los 9 paquetes con su `composer.json`, `ServiceProvider` mínimo y un README.
4. Configurar `deptrac.yaml` con la matriz de la §8.3.
5. Configurar `search_path` por conexión y el comando `cai:migrate` (recorre conexiones).
6. CI en GitHub Actions: `composer install` → `pint --test` → `larastan` → `deptrac` →
   `pest`.
7. Un **arch test** de ejemplo: prohibido `App\Models\*` desde `packages/*`.
8. `docs/ARQUITECTURA-SISTEMA-CAI.md` §7 actualizado a la estructura de paquetes.

**Gate:** CI verde en `main`; un PR de prueba que viola Deptrac **falla** la CI.

**Se pospone:** módulos de negocio.

### F2 — Identidad, permisos y auditoría

**Objetivo:** la base de la seguridad.

Tareas:
1. Migraciones de `identity`: `users`, roles, permisos, `settings`, `audit_events`,
   `security_events`.
2. Trait `Auditable` en `core`: registra `created_by`, `updated_by`, cambios relevantes.
3. `audit_events` con: actor, acción, tipo de entidad, id, diff (JSON), IP, user agent,
   timestamp, resultado.
4. Paneles Filament: usuarios, roles, auditoría (**solo** dirección y admin técnico).
5. Policies base + `BasePolicy`.
6. Mapeo de los 7 roles de dominio a permisos granulares (`billing.payments.create`,
   `care.clinical_notes.view`, …).

**Gate:** un usuario sin permiso **no** accede a la URL directa de un recurso protegido
(test automatizado que lo demuestre).

---

### F3 — Alumnos, tutores y cuentas familiares *(schema `students`)*

**Objetivo:** la ficha del alumno y el modelo de familia.

Tareas:
1. Migraciones `students`: `students`, `guardians`, `student_guardians`, `family_accounts`,
   `family_account_members`, `authorized_pickups`.
2. `student_code` estable y legible; generado con secuencia y checksum.
3. `Contracts/StudentDirectory` + DTOs.
4. Filament: recursos Alumnos, Tutores, Cuentas Familiares.
5. **Importador** de la planilla actual con validación y reporte de rechazos (nunca pisa
   producción; se importa en staging primero).
6. Tests: un alumno puede tener N tutores; una familia puede tener N hijos; historial de
   pertenencia a cuenta.

**Gate:** dos hermanos en la misma cuenta familiar con fichas separadas; un tercero
autorizado a retirar con documento cargado.

---

### F4 — Servicios, profesionales y agenda *(schema `scheduling`)*

**Objetivo:** sesiones individuales y grupales con asistencia.

Tareas:
1. Migraciones `scheduling` (las del §8.4).
2. Regla de no-superposición de horarios (validación en DB con `EXCLUDE USING gist` en
   PostgreSQL: **la mejor garantía** contra doble reserva).
3. Generación de sesiones desde horarios recurrentes (plantillas semanales).
4. Filament: servicios, profesionales, matrículas, grupos, calendario de sesiones.
5. Registro de asistencia por participante (presente/ausente/tarde/justificado).
6. Cancelaciones, reprogramaciones y recuperaciones (sesión nueva enlazada, no se borra la
   original).

**Gate:** una sesión grupal tiene **un** registro de sesión y N registros de asistencia; la
base de datos **rechaza** una superposición de horario del mismo profesional.

---

### F5 — Seguimiento clínico *(schema `care`)*

**Objetivo:** el área de datos sensibles.

Tareas:
1. Migraciones `care`: `care_plans`, `care_plan_professionals`, `care_goals`,
   `clinical_notes`, `clinical_note_access_grants`.
2. Cifrado de aplicación del contenido de `clinical_notes` (cast `encrypted`).
3. Ciclo borrador → finalizada; las finalizadas **no** se editan (corrección = nueva nota
   que referencia la anterior, con motivo).
4. `ClinicalNotePolicy` completa: permiso + asignación vigente + estado.
5. Grants de acceso excepcional: motivo obligatorio, expiración, registro en
   `security_events`.
6. Filament: recursos con **filtros de alcance** (solo alumnos asignados).
7. Prohibición explícita de notas clínicas en exportaciones y widgets generales
   (test que lo comprueba).

**Gate:** un profesional no ve notas de alumnos no asignados; el admin técnico tampoco; toda
lectura sensible queda auditada.

---

### F6 — Finanzas familiares *(schema `billing`)*

**Objetivo:** consistencia del dinero.

Tareas:
1. Migraciones `billing`: `fee_plans`, `charges`, `payments`, `payment_allocations`,
   `receipts`, `receipt_sequences`, `cash_sessions`, `financial_adjustments`.
2. `Action/RegisterPayment`: valida importe, distribuye imputaciones, genera recibo, todo
   en **una transacción**.
3. Numeración de recibos controlada (`receipt_sequences` con `SELECT ... FOR UPDATE`).
4. Imputación automática (FIFO por vencimiento) **y** manual.
5. Anulaciones y ajustes con motivo, sin borrado físico.
6. Sesiones de caja: apertura/cierre, arqueo, diferencia.
7. Filament: cargos, pagos, recibos, estado de cuenta familiar, reportes de deuda.
8. `Money` en `core` con `bcmath`, `NUMERIC(14,2)`, sin floats.

**Gate:** tests de concurrencia (dos pagos simultáneos sobre el mismo cargo no producen
saldo negativo ni doble imputación); una anulación conserva el historial completo.

---

### F7 — Documentos y comunicaciones *(schemas `documents`, `notifications`)*

**Objetivo:** almacenamiento privado y avisos.

Tareas:
1. `documents` con metadatos, categoría, y ruta en `storage/app/private` (**nunca** `public`).
2. Descarga por ruta autenticada con verificación de permisos por documento.
3. `document_access_events` (quién abrió qué, cuándo).
4. `consents` (consentimiento de atención y de tratamiento de datos) con versión y fecha.
5. `notifications`: plantillas, avisos a tutores, recordatorios de cuota/cita como **job**
   en cola.
6. Cola con base de datos (`jobs` table) — **sin Redis** en el MVP.

**Gate:** un documento no es accesible por URL directa sin sesión y permiso; cada descarga
queda auditada.

---

### F8 — Reportes, panel de dirección y delivery

**Objetivo:** indicadores y puesta en operación.

Tareas:
1. `reporting`: solo lectura agregada, consumiendo contratos.
2. Widgets de dirección: alumnos activos, asistencia por periodo, sesiones
   programadas vs. realizadas, recaudación, deuda total, ocupación de profesionales.
3. `release-please` + CHANGELOG + tags SemVer (incluye versionado por paquete).
4. Script `bin/cai release deploy|rollback|status` + symlink `current`.
5. Backups automáticos (diario cifrado + externo) + `bin/cai backup verify`.
6. `docs/RUNBOOK.md` completo + `docs/MANUAL-PERSONAL.md` por rol del centro.
7. Importación final de datos reales en **staging**, validación, y luego producción.
8. **Ensayo de rollback** documentado y cronometrado.

**Gate:** el centro opera, consulta sus informes y **restaura desde una copia probada**.

## 12. Backlog técnico inmediato (primeros 10 días)

Orden de ejecución exacto:

1. `sudo apt install php8.3-bcmath php8.3-gd` y reiniciar PHP-FPM.
2. Verificar matriz de versiones Laravel ↔ Filament ↔ `spatie/laravel-permission` ↔ Pest.
3. `git init` + `.gitignore` + primer commit + repo privado en GitHub + `main` protegida.
4. Escribir los 3 ADRs.
5. `composer create-project laravel/laravel .` (dentro del repo).
6. Instalar Filament + panel.
7. Instalar Pest, Deptrac, Larastan, Pint, `spatie/laravel-permission`.
8. Crear los 9 paquetes + `composer.json` raíz con repos `path`.
9. `deptrac.yaml` + primer arch test.
10. CI en GitHub Actions con los 5 pasos.
11. `config/database.php` con las 9 conexiones + `search_path`.
12. Comando `cai:migrate` y `cai:db:reset`.
13. `docs/RUNBOOK.md` borrador.

**Definition of Done de este backlog:** `main` verde en CI; un PR violando Deptrac falla;
`composer install` limpio en una máquina nueva; `cai:migrate` crea los 9 schemas.

## 14. Glosario

| Término | Significado en este plan |
|---|---|
| **Paquete / módulo** | Directorio en `packages/` con `composer.json` propio, dueño de sus tablas, que expone contratos |
| **Contrato** | Interfaz pública de un módulo; la única forma de leer sus datos desde afuera |
| **Evento de dominio** | Notificación asíncrona entre módulos, con payload plano |
| **Schema** | Namespace de PostgreSQL que aísla las tablas de un módulo |
| **`search_path`** | Lista de schemas donde PostgreSQL busca los objetos sin cualificar |
| **Expand–contract** | Patrón de migración en 3 pasos que garantiza compatibilidad del schema con el release anterior |
| **Kill switch** | Feature flag que apaga una funcionalidad sin redesplegar |
| **Release** | Carpeta versionada en `releases/` apuntada por el symlink `current` |
| **Gate** | Condición verificable que debe cumplirse antes de avanzar de fase |
| **ADR** | Architecture Decision Record: documento breve que registra una decisión y su porqué |
| **Bus factor** | Cuántas personas necesitan entender el sistema para que no se detenga |
