# Convenciones de la Vault

Este documento define cómo se organiza, nombra y enlaza la documentación del proyecto.
Todos los documentos nuevos deben seguir estas reglas.

---

## 1. Estructura de carpetas

```
sistema cai/
├── 00 - Inicio/                  → índice, glosario, plan maestro
├── 01 - Requisitos/              → qué el sistema debe hacer
├── 02 - Arquitectura/            → cómo está construido
├── 03 - Modelo de Datos/         → entidades, tablas, reglas
├── 04 - Seguridad y Privacidad/  → acceso, cifrado, auditoría, legal
├── 05 - Proceso de Desarrollo/   → cómo se trabaja
├── 06 - Versionado y Rollback/   → cómo se versiona y se deshace
├── 07 - Infraestructura/        → servidor, red, backups, operación
├── 08 - Plan de Trabajo/         → fases, tareas, gates, calendario
├── 09 - Manuales del Centro/     → guías por rol (usuarios finales)
├── 10 - Operación/               → runbook, checklists, incidentes
├── 11 - Decisiones ADR/           → decisiones con contexto y consecuencias
├── 12 - Registro de Cambios/     → política, registro, bitácora de IA, versionado
├── 98 - Antecedentes/            → documentos superados, conservados históricamente
└── 99 - Plantillas/              → plantillas reutilizables
```

**Regla:** el número del prefijo define el **orden de lectura**. Un lector nuevo debe poder
recorrer `00 → 01 → 02 → … → 11` en orden y obtener el contexto completo.

---

## 2. Nomenclatura de archivos

```
NN.MM Título en Español.md
│  │  └── Título en español, con mayúscula inicial, sin punto final
│  └── consecutivo dentro de la carpeta (2 dígitos)
└── número de carpeta (2 dígitos)
```

**Reglas adicionales:**
- Los ADR usan un prefijo distinto: `ADR-NNNN Título.md` (ver §4).
- No se usan tildes en los **nombres de archivo** (compatibilidad entre sistemas de
  archivos y URLs). Sí se usan en el contenido.
- No se usan caracteres especiales: `\/:*?"<>|`.
- Máximo 80 caracteres.
- Se usan espacios (no guiones) para legibilidad en el explorador de Obsidian.

---

## 3. Frontmatter

Todo documento lleva metadatos YAML al inicio:

```yaml
---
title: Título del documento
type: moc | convenciones | requisito | arquitectura | datos | seguridad | proceso | configuracion | registro
     | versionado | infraestructura | plan | manual | operacion | adr | plantilla
status: borrador | vigente | deprecated | superseded
tags: [cai, <area>, <tema>]
owner: <rol responsable de mantenerlo>
updated: YYYY-MM-DD
related:
  - "[[Otro Documento]]"
---
```

| Campo | Obligatorio | Significado |
|---|---|---|
| `title` | Sí | Título visible |
| `type` | Sí | Categoría del documento |
| `status` | Sí | `borrador` (en escritura), `vigente` (aprobado), `deprecated` (obsoleto), `superseded` (reemplazado) |
| `tags` | Sí | Etiquetas para búsquedas y consultas de Obsidian |
| `owner` | Sí | Rol que mantiene el documento actualizado |
| `updated` | Sí | Fecha de última revisión |
| `related` | No | Enlaces a documentos cercanos |

**Transición obligatoria:** `borrador` → `vigente` solo cuando el documento es aprobado
explícitamente por el responsable. Un documento `borrador` **no** es referencia para
implementar.

## 4. ADR (Architecture Decision Records)

```
11 - Decisiones ADR/Índice de ADRs.md
11 - Decisiones ADR/ADR-0001 Título Corto.md
```

Cada ADR sigue la plantilla [[Plantilla - ADR]] y contiene:

| Sección | Contenido |
|---|---|
| Contexto | Qué problema o restricción motivó la decisión |
| Decisión | Qué se decidió, en una frase |
| Alternativas consideradas | Con el motivo de descarte |
| Consecuencias | Qué se gana, qué se pierde, qué obligaciones aparecen |
| Estado | `borrador` · `aceptado` · `revisado` · `reemplazado` · `descartado` |

El índice [[Índice de ADRs]] es el **MOC** de la carpeta: lista los ADR
existentes, los agrupa por dominio y enumera las decisiones **pendientes** de
ADR (las que dependen de una respuesta de Dirección).

**Regla:** una decisión no obvia que afecte la estructura, el modelo de datos, la seguridad o
el versionado **debe** tener un ADR. Si no, se decide en el hilo del chat y se pierde.

## 5. Enlaces (wikilinks)

Se usan **wikilinks** de Obsidian, no URLs de Markdown:

```markdown
[[02.03 Reglas de Frontera entre Módulos]]
[[02.03 Reglas de Frontera entre Módulos|las reglas de frontera]]
```

**Reglas:**
- El enlace apunta al **nombre de archivo sin extensión**.
- En la primera mención de un documento importante dentro de un párrafo, se lo enlaza.
- Los documentos de referencia cruzada se enlazan desde la sección **"Documentos
  relacionados"** al final.
- No se enlazan archivos de código desde la documentación; se menciona la ruta en `código`.

---

## 6. Bloques de llamada

Se usan para marcar información que no se puede perder:

```markdown
> [!important] Importante
> Texto que define el comportamiento esperado.

> [!warning] Riesgo
> Algo que puede romper el sistema si se ignora.

> [!danger] Datos sensibles
> Información que no debe salir del área controlada.

> [!example] Ejemplo
> Caso concreto.

> [!question] Definir
> Pregunta abierta pendiente de respuesta.

> [!tip] Consejo
> Recomendación práctica.
```

---

## 7. Tablas

- Siempre con **fila de encabezado** y separador `|---|`.
- Primera columna alineada a la izquierda, columnas numéricas a la derecha.
- Los identificadores de requisitos se escriben en negrita: `**RF-012**`.

---

## 8. Bloques de código

- Siempre con el lenguaje declarado: ```` ```php ````, ```` ```sql ````, ```` ```bash ````,
  ```` ```yaml ````, ```` ```mermaid ````.
- **En esta bóveda el código es ilustrativo.** Los bloques muestran la forma que tendrá la
  implementación; el código real vive en el repositorio, no acá.
- Toda pieza de código debe ir acompañada de una nota que explique **por qué** existe.

---

## 9. Diagramas

Se usan diagramas Mermaid cuando aportan:

````markdown
```mermaid
flowchart LR
  A[Alumno] --> B[Matrícula]
  B --> C[Sesión]
```
````

**Regla:** un diagrama debe ir acompañado de una explicación en prosa. Un diagrama sin
explicación no se mantiene.

---

## 10. Etiquetas (tags)

| Etiqueta | Significado |
|---|---|
| `#cai` | Pertenece al sistema CAI |
| `#obsoleto` | Documento desactualizado, slated for rewrite |
| `#bloqueante` | Su resolución bloquea el avance de una fase |
| `#legal` | Requiere revisión de asesoría jurídica |
| `#operacion` | Relacionado con la operación diaria del sistema |
| `#seguridad` | Relacionado con acceso, datos sensibles o auditoría |

---

## 11. Proceso de cambio

1. Se edita el documento afectado y su `updated`.
2. Si el cambio invalida otro documento → se actualiza ese también, en el mismo momento.
3. Si el cambio altera una decisión → se crea un **nuevo ADR** y el anterior pasa a
   `superseded` con la referencia al nuevo.
4. Los documentos del centro (`09 - Manuales`) los valida el usuario final correspondiente
   antes de marcarlos `vigente`.
