# Eventos de Dominio

> [!info] Propósito
> Formalizar cómo los módulos se comunican entre sí sin acoplamiento directo.
> Los eventos permiten reaccionar a hechos pasados sin que el emisor conozca
> a los receptores.

---

## 1. Principios

| Principio | Explicación |
|---|---|
| **Hecho, no comando** | Un evento describe algo que **ya ocurrió** (`StudentRegistered`), no una orden (`RegisterStudent`). |
| **Desacoplamiento** | El emisor no importa clases del receptor. Solo se importa el evento. |
| **Payload plano** | Sin modelos Eloquent. Solo escalares, enums serializables, DTOs planos o arrays. |
| **Sin datos clínicos** | Nunca transportar contenido de `clinical_notes`. Solo identificadores y metadatos no sensibles. |
| **Post-commit** | Siempre `ShouldDispatchAfterCommit`. Si la transacción hace rollback, el evento **no** se envía. |
| **Inmutable** | El payload no se modifica tras el despacho. Los listeners reaccionan, no mutan el pasado. |

---

## 2. Dónde viven

```text
packages/<modulo>/src/Events/
├── StudentRegistered.php
└── ...
```

Cada evento pertenece al **módulo emisor**. Los listeners viven en el módulo
consumidor dentro de `src/Listeners/` y se registran en el `ServiceProvider`
del consumidor.

---

## 3. Implementación

```php
<?php

declare(strict_types=1);

namespace Cai\Students\Events;

use Illuminate\Broadcasting\InteractsWithSockets;
use Illuminate\Contracts\Events\ShouldDispatchAfterCommit;
use Illuminate\Foundation\Events\Dispatchable;
use Illuminate\Queue\SerializesModels;

final class StudentRegistered implements ShouldDispatchAfterCommit
{
    use Dispatchable;
    use InteractsWithSockets;
    use SerializesModels;

    public function __construct(
        public readonly int $studentId,
        public readonly string $studentCode,
        public readonly int $familyAccountId,
        public readonly string $registeredAt, // ISO8601
    ) {
    }
}
```

**Reglas:**

- Implementar `ShouldDispatchAfterCommit`.
- Usar `final` en la clase.
- Propiedades `public readonly`.
- Sin tipos Eloquent (`Student`, `User`, etc.).
- Sin datos clínicos, financieros sensibles o contraseñas.
- Fechas como `string` ISO8601 o `Carbon` serializable, nunca objetos complejos.

## 4. Catálogo de eventos

| Evento | Emisor | Consumidores | Descripción | Estado |
|---|---|---|---|---|
| `StudentRegistered` | `students` | `billing` (crear cuenta/cargo inicial si aplica), `notifications` (bienvenida) | Alumno dado de alta en el sistema | Planificado |
| `StudentTransferredToAccount` | `students` | `billing` (recalcular pertenencia) | Alumno cambia de cuenta familiar | Planificado |
| `EnrollmentCreated` | `scheduling` | `billing` (generar cargo), `care` (ofrecer crear plan) | Matrícula activa | Planificado |
| `EnrollmentEnded` | `scheduling` | `billing` (cerrar cargo / saldo) | Matrícula finalizada o dada de baja | Planificado |
| `SessionScheduled` | `scheduling` | `notifications` (aviso) | Sesión agendada | Planificado |
| `SessionCompleted` | `scheduling` | `care` (ofrecer redactar nota), `billing` (facturar por unidad según convenio) | Sesión realizada | Planificado |
| `SessionCancelled` | `scheduling` | `notifications` (aviso a familia), `billing` (ajuste si aplica) | Sesión cancelada | Planificado |
| `PaymentRegistered` | `billing` | `notifications` (enviar recibo) | Pago registrado e imputado | Planificado |
| `PaymentVoided` | `billing` | `notifications` (aviso) | Pago anulado con motivo | Planificado |
| `ClinicalNoteFinalized` | `care` | `notifications` (aviso opcional, **sin contenido**) | Nota clínica finalizada | Planificado |
| `DocumentUploaded` | `documents` | `notifications` (aviso), `identity` (auditoría) | Documento subido | Planificado |

> [!warning] Prohibido
> `ClinicalNoteCreated`, `ClinicalNoteViewed` con contenido, o cualquier evento
> que transporte `content`, `diagnosis` o texto clínico.

## 5. Versionado

Cuando el payload cambia de forma incompatible:

1. Crear un nuevo evento `EventoV2` con el nuevo contrato.
2. El emisor puede despachar **ambos** durante la transición (o migrar consumidores primero).
3. Los listeners antiguos se eliminan cuando ya no haya productores del `EventoV1`.
4. Documentar el cambio en el registro de cambios y, si es relevante, en un ADR.

**Ejemplo:** `PaymentRegisteredV2` si se añaden campos obligatorios.

---

## 6. Listeners y colas

| Regla | Detalle |
|---|---|
| **Asíncrono cuando convenga** | Notificaciones pueden ir a cola (`ShouldQueue`). Operaciones críticas financieras que requieran consistencia inmediata van **síncronas** o con `afterCommit`. |
| **Idempotentes** | Un listener debe poder ejecutarse dos veces sin efectos duplicados (usar claves únicas o verificar estado). |
| **Manejar fallos** | Si falla un listener en cola, usar `failed_jobs` con reintento controlado. El hecho original **ya está registrado**. |
| **Sin transacciones cruzadas** | El listener NO abre transacciones que afecten al módulo emisor. Trabaja en su propio esquema. |

## 7. Verificación

| Comprobación | Cómo |
|---|---|
| **Arch test A-03** | Eventos sin modelos Eloquent |
| **Arch test A-04** | Sin datos clínicos en eventos ajenos a `care` |
| **Deptrac** | El acoplamiento es por evento, no por import de clase entre módulos |
| **Revisión** | Todo nuevo evento pasa por revisión con esta lista de verificación |

**Checklist al añadir un evento:**

- [ ] Pertenece al módulo emisor
- [ ] Implementa `ShouldDispatchAfterCommit`
- [ ] Payload plano, sin Eloquent
- [ ] Sin datos clínicos
- [ ] Nombrado como hecho pasado (`PastTenseVerb`)
- [ ] Documentado en la tabla §4
- [ ] Listeners idempotentes si van a cola
