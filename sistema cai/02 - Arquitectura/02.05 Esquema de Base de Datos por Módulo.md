# Esquema de Base de Datos por Módulo

---

## 1. Decisión

**Cada módulo tiene su propio schema de PostgreSQL**, y **una conexión de base de datos
por módulo** con `search_path` propio.

| Schema | Dueño | Tablas |
|---|---|---|
| `core` | — | (reservado, sin tablas) |
| `identity` | `cai/identity` | `users`, `roles`, `permissions`, `model_has_roles`, `model_has_permissions`, `role_has_permissions`, `settings`, `feature_flags`, `audit_events`, `security_events` |
| `students` | `cai/students` | `students`, `guardians`, `student_guardians`, `family_accounts`, `family_account_members`, `authorized_pickups` |
| `scheduling` | `cai/scheduling` | `services`, `professionals`, `enrollments`, `groups`, `group_memberships`, `sessions`, `session_professionals`, `session_participants`, `attendance_records`, `availability_rules` |
| `care` | `cai/care` | `care_plans`, `care_plan_professionals`, `care_goals`, `clinical_notes`, `clinical_note_access_grants` |
| `documents` | `cai/documents` | `documents`, `document_access_events`, `consents` |
| `billing` | `cai/billing` | `fee_plans`, `charges`, `payments`, `payment_allocations`, `receipts`, `receipt_sequences`, `cash_sessions`, `financial_adjustments` |
| `notifications` | `cai/notifications` | `notifications`, `message_templates` |
| `reporting` | `cai/reporting` | (vistas materializadas opcionales; se agregan si hacen falta) |

---

## 2. Por qué `search_path` y no nombres cualificados

PostgreSQL permite `billing.charges` o simplemente `charges` con `search_path = billing`.

**Se elige `search_path`** por una razón práctica concreta: **el constructor de schemas de
Laravel no maneja bien los nombres cualificados**.

| Operación | Con `search_path` | Con nombre cualificado (`billing.charges`) |
|---|---|---|
| `Schema::create('charges')` | ✅ `billing.charges` | ✅ `billing.charges` |
| `Schema::hasTable('charges')` | ✅ correcto | ❌ **falso negativo** (busca `schemaname = current_schema()` con el nombre completo) |
| `Schema::dropIfExists('charges')` | ✅ correcto | ❌ no borra |
| `migrate:fresh` | ✅ borra el schema del módulo | ❌ **no borra nada** (solo ve `current_schemas()`) |

> [!danger] Gotcha G1 y G2
> Con nombres cualificados, `hasTable()` devuelve `false` y `migrate:fresh` **deja las
> tablas viejas en pie**, produciendo estados inconsistentes entre entornos. Con
> `search_path`, todo el toolkit de Laravel funciona nativamente.
>
> Ver la lista completa de gotchas en [[06.02 Versionado de Esquema de BD]].

## 3. Configuración de las conexiones

```php
// config/database.php
'connections' => [
    'pgsql' => [
        'driver' => 'pgsql',
        'host' => env('DB_HOST', '127.0.0.1'),
        'port' => env('DB_PORT', '5432'),
        'database' => env('DB_DATABASE', 'cai'),
        'username' => env('DB_USERNAME', 'cai'),
        'password' => env('DB_PASSWORD'),
        'charset' => 'utf8',
        'prefix' => '',
        'prefix_indexes' => true,
        'search_path' => 'public',
        'search_path_setting' => true,
        'sslmode' => 'prefer',
    ],

    // Una conexión por módulo. Todas apuntan a la misma base,
    // pero con un search_path distinto.
    'students' => [
        'driver' => 'pgsql',
        'host' => env('DB_HOST', '127.0.0.1'),
        'port' => env('DB_PORT', '5432'),
        'database' => env('DB_DATABASE', 'cai'),
        'username' => env('DB_USERNAME', 'cai'),
        'password' => env('DB_PASSWORD'),
        'charset' => 'utf8',
        'prefix' => '',
        'search_path' => 'students, public',
        'search_path_setting' => true,
    ],

    'scheduling' => [ /* ... 'search_path' => 'scheduling, public' */ ],
    'care'       => [ /* ... 'search_path' => 'care, public' */ ],
    'billing'    => [ /* ... 'search_path' => 'billing, public' */ ],
    'documents'  => [ /* ... 'search_path' => 'documents, public' */ ],
    'notifications' => [ /* ... */ ],
    'reporting'  => [ /* ... */ ],
],
```

> [!warning] `search_path` incluye `public`
> Se incluye `public` como fallback para las extensiones de PostgreSQL (`pgcrypto`,
> `citext`, etc.) que pueden vivir ahí. **Ninguna tabla de negocio va en `public`.**

## 4. Modelos: la conexión se declara siempre

```php
namespace Cai\Billing\Models;

use Illuminate\Database\Eloquent\Model;

final class Charge extends Model
{
    // La conexión define el schema. Es OBLIGATORIA.
    protected $connection = 'billing';

    protected $table = 'charges';

    protected $fillable = ['family_account_id', 'student_id', 'enrollment_id', 'description', 'period', 'due_date', 'amount', 'status'];

    protected $casts = [
        'amount'   => 'decimal:2',
        'due_date' => 'date',
        'period'   => 'date',
    ];
}
```

**Regla:** todo modelo declara `protected $connection`. Sin excepción. Es la línea que
impide que un modelo de `billing` termine escribiendo en `students`.

## 5. Aislamiento real: qué puede y qué no puede hacer un módulo

| Acción | `billing` (schema `billing`) | Resultado |
|---|---|---|
| `SELECT * FROM charges` | ✅ | Resuelve a `billing.charges` |
| `SELECT * FROM students` | ❌ | *relation "students" does not exist* |
| `SELECT * FROM students.students` | ⚠️ | Funciona (requiere cualificación explícita) — **prohibido por Deptrac/revisión** |
| `INSERT INTO students.students ...` | ⚠️ | Funciona técnicamente — **prohibido** |

> [!important] La diferencia con un monolito clásico
> En un monolito con todo en `public`, `billing` **puede** escribir en `students` sin
> esfuerzo. Con schemas separados, esa escritura requiere una acción consciente
> (cualificar el schema). No es una barrera de seguridad absoluta, pero **convierte la
> violación en algo visible** en el código y detectable en la revisión.

## 6. Claves foráneas cross-schema

**Se permiten**, para proteger la integridad del historial.

```php
// En la migración de cai/billing
$table->foreignId('student_id')
    ->constrained('students.students')   // ← cross-schema
    ->restrictOnDelete();

$table->foreignId('family_account_id')
    ->constrained('students.family_accounts')
    ->restrictOnDelete();
```

**Motivo:** un alumno con historial financiero **no debe poder eliminarse**. La FK con
`RESTRICT` lo impide a nivel de motor, sin depender de la disciplina de la aplicación.

**Riesgo aceptado:** si se eliminara el schema `students` completo, las FKs de `billing`
lo bloquearían. **Esto es intencional:** el schema `students` no se elimina nunca (es la
identidad del centro). Para una eliminación hipotética de un módulo, el orden es: primero sus
consumidores.

**Alternativa considerada y descartada:** sin FKs cross-schema, la integridad depende de la
aplicación → un bug permite ReferenceOrphans. Se prefiere la garantía del motor.

## 7. Commandos propios

Dos comandos reemplazan la falta de herramientas de Laravel para schemas:

```bash
# Crea los schemas y ejecuta las migraciones de cada módulo en orden.
php artisan cai:migrate

# Equivalente a migrate:fresh, pero respetando los schemas por módulo.
php artisan cai:db:reset

# Estado: migraciones aplicadas por módulo, revisión de la base.
php artisan cai:db:status
```

`cai:migrate` recorre las conexiones en orden de dependencia:

```
identity → students → scheduling → care → documents → billing → notifications → reporting
```

**Por qué el orden importa:** `billing` referencia `students.students`, y `students`
referencia `identity.users`. El orden garantiza que las FKs se pueden crear.

## 8. Backups por módulo

```bash
# Backup de un solo módulo (no incluye datos clínicos si es el correcto)
pg_dump --schema=billing    -Fc cai > backup_billing.dump
pg_dump --schema=students   -Fc cai > backup_students.dump

# Backup de la base completa
pg_dump -Fc cai > backup_completo.dump
```

**Regla operativa:** los backups de **producción** se hacen **por módulo**, cada uno
cifrado por separado. Así:
1. Un backup de `billing` **no expone notas clínicas**.
2. La restauración se puede hacer módulo por módulo.
3. Se puede verificar la integridad de un módulo sin tocar los demás.

Ver [[06.07 Backups y Recuperación]].

## 9. Restricciones cross-schema y `search_path` — resumen de lo que hay que recordar

| # | Recordatorio |
|---|---|
| 1 | El schema por módulo **no** impide el acceso directo por SQL. Impide el acceso **por comodidad** y lo hace visible. La barrera fuerte es Deptrac + arch tests + code review. |
| 2 | Las FKs cross-schema sí están permitidas y son deseables para integridad. |
| 3 | `migrate:fresh` **no** borra los schemas de los módulos → usar `cai:db:reset`. |
| 4 | Cada modelo declara `protected $connection`. |
| 5 | Las conexiones se configuran una vez en `config/database.php`, no por paquete. |
| 6 | Los tests usan `RefreshDatabase` con **todas** las conexiones listadas. |
