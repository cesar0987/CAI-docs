# Arquitectura Modular en Paquetes

---

## 1. Por qué paquetes y no carpetas

Con la estructura clásica `app/Domain/Students/...`, el siguiente código **funciona** y
**no rompe ningún test**:

```php
// En el módulo de facturación, importando el modelo de alumnos:
use App\Domain\Students\Models\Student;

$student = Student::find($id);
```

Ese es el problema. La frontera existe solo en la cabeza del desarrollador. El primer día
que alguien tiene prisa, la cruza — y la Modularidad se convierte en una aspiración.

Con **paquetes Composer**:

```php
// En el módulo de facturación:
use Cai\Students\Contracts\StudentDirectory;   // ✅ contrato
use Cai\Students\Contracts\Dto\StudentSummary;  // ✅ DTO

// use Cai\Students\Models\Student;             // ❌ no existe en su autoload
```

La clase no se resuelve. **El error aparece al compilar, no en producción.** Y como la CI
corre Deptrac sobre el grafo de dependencias, la frontera se detecta antes del merge.

## 2. Los 9 paquetes

| Paquete | Schema | Responsabilidad | Contiene |
|---|---|---|---|
| `cai/core` | — | Kernel compartido | Modelo base, traits, `Money`, contratos base, auditoría |
| `cai/identity` | `identity` | Identidad y control de acceso | `users`, roles, permisos, `settings`, `feature_flags`, `audit_events`, `security_events` |
| `cai/students` | `students` | Quién es el alumno y su familia | `students`, `guardians`, `student_guardians`, `family_accounts`, `family_account_members`, `authorized_pickups` |
| `cai/scheduling` | `scheduling` | Qué se atiende, cuándo y quién asiste | `services`, `professionals`, `enrollments`, `groups`, `group_memberships`, `sessions`, `session_professionals`, `session_participants`, `attendance_records` |
| `cai/care` | `care` | La atención profesional y sus registros | `care_plans`, `care_plan_professionals`, `care_goals`, `clinical_notes`, `clinical_note_access_grants` |
| `cai/billing` | `billing` | El dinero | `fee_plans`, `charges`, `payments`, `payment_allocations`, `receipts`, `receipt_sequences`, `cash_sessions`, `financial_adjustments` |
| `cai/documents` | `documents` | Los archivos y los permisos sobre ellos | `documents`, `document_access_events`, `consents` |
| `cai/notifications` | `notifications` | La comunicación con las familias | `notifications`, `message_templates` |
| `cai/reporting` | `reporting` | La lectura agregada para decidir | Reportes, widgets, indicadores |

## 3. Estructura del repositorio

```
cai/
├── app/                          # HOST LARAVEL (delgado)
│   ├── Filament/                 # clusters, páginas transversales, panel principal
│   ├── Providers/
│   │   ├── AppServiceProvider.php
│   │   └── Filament/AdminPanelProvider.php
│   ├── Http/Middleware/
│   └── Http/Controllers/         # solo lo que no pertenece a ningún paquete
│
├── packages/
│   ├── core/
│   ├── identity/
│   ├── students/
│   ├── scheduling/
│   ├── care/
│   ├── billing/
│   ├── documents/
│   ├── notifications/
│   └── reporting/
│
├── config/                       # configuración del host + merge de los paquetes
├── database/
│   ├── migrations/               # solo migraciones del host (casi vacío)
│   ├── seeders/                  # datos iniciales del sistema (roles, permisos, config)
│   └── factories/
├── routes/
│   ├── web.php
│   ├── api.php                   # preparado para el portal familiar (etapa 2)
│   └── console.php
├── resources/
│   ├── views/
│   └── css/  js/
├── tests/                        # tests del host: Architecture, Smoke, Integración
├── storage/
├── bin/                          # scripts de operación
├── docs/                         # esta bóveda (copia o submódulo)
├── composer.json
├── deptrac.yaml
├── phpunit.xml
├── pint.json
└── .github/workflows/
```

> [!note] Por qué `app/` es delgado
> El host solo compone: registra providers, define el panel de Filament y enruta. **Toda
> la lógica de negocio vive en los paquetes.** Si mañana el portal familiar de Next.js
> necesita la lógica, la consume vía API sin tocar el host.

## 5. El `composer.json` de un paquete

```json
{
  "name": "cai/students",
  "description": "Alumnos, tutores y cuentas familiares del Centro de Atencion Inclusiva.",
  "type": "library",
  "license": "proprietary",
  "version": "1.0.0",
  "require": {
    "php": "^8.3",
    "illuminate/support": "^12.0",
    "illuminate/database": "^12.0",
    "cai/core": "*"
  },
  "require-dev": {
    "pestphp/pest": "^3.0",
    "pestphp/pest-plugin-laravel": "^3.0"
  },
  "autoload": {
    "psr-4": { "Cai\\Students\\": "src/" }
  },
  "autoload-dev": {
    "psr-4": { "Cai\\Students\\Tests\\": "tests/" }
  },
  "extra": {
    "laravel": {
      "providers": ["Cai\\Students\\Providers\\StudentsServiceProvider"]
    }
  },
  "minimum-stability": "stable",
  "prefer-stable": true
}
```

**Puntos importantes:**
- `version` explícita → permite versionado semántico **por paquete**.
- `extra.laravel.providers` → Laravel auto-descubre el ServiceProvider.
- El paquete **no** declara `illuminate/console` ni `illuminate/routing` porque no expone
  comandos ni rutas propias. Si los necesita, los declara explícitamente.

```json
{
  "name": "cai/sistema",
  "type": "project",
  "require": {
    "php": "^8.3",
    "cai/core": "*",
    "cai/identity": "*",

    "cai/billing": "*",
    "cai/documents": "*",
    "cai/notifications": "*",
    "cai/reporting": "*"

  "repositories": [
    { "type": "path", "url": "packages/core",        "options": { "symlink": true } },
    { "type": "path", "url": "packages/identity",    "options": { "symlink": true } },
    { "type": "path", "url": "packages/students",    "options": { "symlink": true } },
    { "type": "path", "url": "packages/scheduling",  "options": { "symlink": true } },
    { "type": "path", "url": "packages/care",        "options": { "symlink": true } },
    { "type": "path", "url": "packages/billing",     "options": { "symlink": true } },
    { "type": "path", "url": "packages/documents",   "options": { "symlink": true } },
    { "type": "path", "url": "packages/notifications","options": { "symlink": true } },
    { "type": "path", "url": "packages/reporting",   "options": { "symlink": true } }
  ],
  "autoload": {
    "psr-4": { "App\\": "app/" }
  },
  "scripts": {
    "test": "pest",
    "analyse": "larastan analyse",
    "deptrac": "deptrac analyse --config-file=deptrac.yaml",
    "lint": "pint --test"
  }
}
```

> [!important] Symlink en desarrollo, copia en producción
> En **desarrollo**, `symlink: true` hace que los cambios en `packages/` se reflejen
> instantáneamente. En **producción** el deploy usa `COMPOSER_MIRROR_PATH_REPOS=1`, que
> **copia** los paquetes dentro de cada release. Así cada release es autocontenido y el
> rollback por symlink funciona de verdad. Ver [[06.05 Release y Deploy]].

## 7. El ServiceProvider de un paquete

```php
<?php

namespace Cai\Students\Providers;

use Cai\Students\Models\Student;
use Illuminate\Support\ServiceProvider;

class StudentsServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        $this->mergeConfigFrom(__DIR__.'/../../config/students.php', 'students');
    }

    public function boot(): void
    {
        $this->loadMigrationsFrom(__DIR__.'/../../database/migrations');
        $this->loadViewsFrom(__DIR__.'/../../resources/views', 'students');

        Student::observe(StudentObserver::class);
    }
}
```

**Reglas:**
- El provider **no** registra rutas ni panel: eso lo hace el host o el propio paquete si
  expone un recurso de Filament (que se registra desde `app/Filament`, no desde el package,
  para mantenerlo simple en el MVP).
- Las migraciones se cargan con `loadMigrationsFrom` y se ejecutan **por schema**
  (ver [[02.05 Esquema de Base de Datos por Módulo]]).

## 8. Cuándo crear un paquete nuevo

> [!tip] Regla de contención
> **No se crea un paquete hasta que un módulo tenga ≥ 3 clases y un consumidor real.**
> Con un solo dev part-time, la ceremonia de empaquetar se paga sola cuando el módulo
> justifica el costo.

| Situación | Acción |
|---|---|
| Funcionalidad nueva dentro de un módulo existente | **Agregar al paquete existente** |
| Módulo con 3+ clases y un consumidor externo | Crear paquete nuevo |
| Funcionalidad que se va a reutilizar en el portal familiar | Crear paquete nuevo (para que la lógica quede accesible por API) |
| Funcionalidad que necesita su propio schema | Crear paquete nuevo |

## 9. Versionado por paquete

Cada paquete tiene su versión SemVer independiente:

| Paquete | v1.0.0 | v1.1.0 | v2.0.0 |
|---|---|---|---|
| `cai/core` | versión inicial | agregar helper | cambiar firma de un contrato |
| `cai/students` | versión inicial | nuevo campo en un DTO | cambiar `StudentDirectory::find()` |

**Reglas:**
- Cambio de comportamiento observable → **MINOR**.
- Cambio incompatible de un contrato público → **MAJOR** + nota en el CHANGELOG.
- Los demás paquetes que dependen del contrato afectado deben actualizarse.

`release-please` con configuración de monorepo bumpea automáticamente la versión de cada
paquete según los cambios en su directorio.

## 10. Consecuencias y límites

### Ventajas
- **Fronteras verificables** por CI (Deptrac), no por convención.
- **Reutilización directa** para el portal familiar de la etapa 2.
- **Depuración acotada**: un bug en `billing` no toca `care`.
- **Onboarding** por paquete, no por todo el sistema.
- **Extracción posible**: `pg_dump -n billing` + el paquete = un módulo portable.

### Límites conocidos y aceptados
- **Transacciones no cruzan módulos.** La atomicidad crítica vive dentro de `billing`.
  La comunicación entre módulos es por eventos post-commit, con listeners idempotentes.
- **Overhead de ceremonia.** Mitigado por la regla de contención (§8).
- **Acoplamiento vía eventos.** Un cambio en la forma de un evento rompe al listener. Se
  mitiga con versionado de eventos: `StudentRegisteredV1` → `V2`.
