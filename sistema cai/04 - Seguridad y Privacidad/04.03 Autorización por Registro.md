# Autorización por Registro

> [!important] La diferencia
> El **permiso** responde *"¿qué puede hacer esta persona en general?"*.
> La **autorización por registro** responde *"¿puede hacerlo **sobre este alumno, esta
> sesión, esta cuenta** en particular?"*.
>
> Sin la segunda capa, un profesional vería **todos** los alumnos. Sin la primera, Dirección
> no vería nada.

---

## 1. El patrón

```php
namespace Cai\Care\Policies;

use Cai\Care\Models\ClinicalNote;
use Cai\Identity\Models\User;

final class ClinicalNotePolicy
{
    /**
     * ¿Puede el usuario ver cualquier nota en el listado?
     */
    public function viewAny(User $user): bool
    {
        return $user->hasPermissionTo('care.notes.view');
    }

    /**
     * ¿Puede el usuario ver ESTA nota?
     */
    public function view(User $user, ClinicalNote $note): bool
    {
        // Capa 1: permiso
        if (! $user->hasPermissionTo('care.notes.view')) {
            return false;
        }

        // Excepción 1: el autor siempre accede a lo suyo
        if ($note->author_user_id === $user->id) {
            return true;
        }

        // Excepción 2: acceso excepcional concedido y vigente
        if ($note->hasActiveGrantFor($user->id)) {
            return true;
        }

        // Capa 2: alcance — asignación profesional vigente sobre el alumno
        return $user->hasActiveClinicalAssignmentFor($note->student_id);
    }

    public function create(User $user): bool
    {
        return $user->hasPermissionTo('care.notes.create')
            && $user->hasActiveProfessionalProfile();
    }

    public function update(User $user, ClinicalNote $note): bool
    {
        return $note->status === \Cai\Care\Enums\ClinicalNoteStatus::Draft
            && $note->author_user_id === $user->id
            && $user->hasPermissionTo('care.notes.create');
    }

    /**
     * No se borra. La nota en borrador se descarta (soft delete),
     * la finalizada se corrige con una nota nueva.
     */
    public function delete(User $user, ClinicalNote $note): bool
    {
        return false;
    }
}
```

**Reglas de la plantilla de Policy:**

| # | Regla |
|---|---|
| 1 | El permiso se verifica **primero**, siempre |
| 2 | El alcance se verifica **después** |
| 3 | La negación es temprana (`if (! ...) return false;`) |
| 4 | Todo `true` va acompañado de la razón (comentario o método con nombre claro) |
| 5 | `delete` nunca devuelve `true` en entidades con historial |
| 6 | La Policy **no escribe** en la base ni tiene efectos secundarios |
| 7 | La Policy es **determinista**: mismos inputs → mismo resultado |

## 2. Policy por módulo

### 2.1 `students` — `StudentPolicy`

```php
public function view(User $user, Student $student): bool
{
    if (! $user->hasPermissionTo('students.students.view')) {
        return false;
    }

    // Dirección, Coordinación, Secretaría: acceso total.
    // Profesional: solo alumnos con asignación vigente.
    // Finanzas: acceso mínimo (manejado por un Resource separado).
    return $user->hasPermissionTo('care.clinical.read')
        ? true
        : $user->hasActiveProfessionalAssignmentFor($student->id);
}
```

### 2.2 `students` — `GuardianPolicy`

```php
public function update(User $user, Guardian $guardian): bool
{
    if (! $user->hasPermissionTo('students.guardians.manage')) {
        return false;
    }

    // Recepción solo puede actualizar el teléfono de contacto,
    // y solo de alumnos que gestiona.
    if ($user->hasRole('recepcion')) {
        return $user->canOnlyUpdateContactFieldsOf($guardian);
    }

    return true;
}
```

### 2.3 `scheduling` — `SessionPolicy`

```php
public function recordAttendance(User $user, Session $session): bool
{
    if (! $user->hasPermissionTo('scheduling.attendance.record')) {
        return false;
    }

    $assignment = $session->assignmentFor($user->professional_id);

    if ($assignment === null) {
        return false;
    }

    // Solo el responsable, o el asistente cuando el responsable no está.
    return $assignment->assignment_role === 'responsible'
        || ($assignment->assignment_role === 'assistant' && ! $session->hasResponsibleAssigned());
}
```

### 2.4 `billing` — `PaymentPolicy`

```php
public function void(User $user, Payment $payment): bool
{
    if (! $user->hasPermissionTo('billing.payments.void')) {
        return false;
    }

    // Solo se anula un pago del mismo día (o con autorización de Dirección).
    if ($payment->paid_at->isToday()) {
        return true;
    }

    return $user->hasPermissionTo('billing.charges.adjust');
}
```

### 2.5 `documents` — `DocumentPolicy`

```php
public function download(User $user, Document $document): bool
{
    if (! $user->hasPermissionTo('documents.documents.download')) {
        return false;
    }

    // Categorías clínicas: solo rol clínico con alcance.
    if ($document->is_clinical_category()) {
        return $user->hasPermissionTo('care.documents.view')
            && $this->hasClinicalScope($user, $document);
    }

    // Categoría financiera: solo Finanzas.
    if ($document->category === DocumentCategory::Financial) {
        return $user->hasPermissionTo('billing.receipts.view');
    }

    // Resto: cualquier usuario con el permiso y con relación con la entidad.
    return true;
}
```

### 2.6 `care` — `CarePlanPolicy`

```php
public function view(User $user, CarePlan $plan): bool
{
    if (! $user->hasPermissionTo('care.plans.view')) {
        return false;
    }

    // Cualquier profesional del plan lo ve.
    if ($plan->hasProfessional($user->professional_id)) {
        return true;
    }

    // Grace period: tras el cierre, el profesional mantiene acceso
    // a los planes que redactó, para poder consultarlos.
    return $plan->responsible_professional_id === $user->professional_id
        && $plan->closed_at?->diffInDays(now()) < 90;
}
```

## 3. El scope: segunda barrera para los listados

Una Policy protege **una acción**. Para **listados**, hace falta además que la consulta no
devuelva lo que el usuario no puede ver.

### 3.1 Definición del scope

```php
namespace Cai\Identity\Models;

use Illuminate\Database\Eloquent\Builder;

final class User extends Authenticatable
{
    /**
     * Alcance de alumnos visibles para este usuario.
     */
    public function scopeVisibleStudents(Builder $query): Builder
    {
        // Roles con visión global.
        if ($this->hasPermissionTo('care.clinical.read')
            || $this->hasRole('direccion')
            || $this->hasRole('secretaria')) {
            return $query;
        }

        // Profesional: solo alumnos con asignación vigente.
        if ($this->hasRole('profesional')) {
            return $query->whereIn('id', $this->assignedStudentIds());
        }

        // Recepción: sin acceso al listado de alumnos.
        return $query->whereRaw('1 = 0');
    }

    public function assignedStudentIds(): array
    {
        return DB::connection('scheduling')
            ->table('professional_assignments')
            ->where('professional_id', $this->professional_id)
            ->where(fn ($q) => $q->whereNull('valid_until')->orWhere('valid_until', '>=', today()))
            ->distinct()
            ->pluck('student_id')
            ->all();
    }
}
```

### 3.2 Aplicación en Filament

```php
protected static function getEloquentQuery(): Builder
{
    return parent::getEloquentQuery()->visibleStudents();
}
```

### 3.3 Regla del scope

| Regla | Detalle |
|---|---|
| **El listado se filtra siempre** | Un listado sin scope es una fuga masiva |
| **El scope no reemplaza la Policy** | Scope = 1ª barrera; Policy = 2ª barrera |
| **Las exportaciones respetan el scope** | Una exportación sin scope es la peor fuga posible |
| **La búsqueda global excluye lo clínico** | Filament `GlobalSearch` no incluye `ClinicalNote` |
| **Los selectores también se filtran** | Un `<select>` de alumnos sin scope también filtra |

> [!danger] El caso más frecuente de fuga
> El formulario de una sesión grupal tiene un selector de participantes. Si ese selector
> no está filtrado por scope, un profesional ve la lista de **todos** los alumnos del
> centro, aunque no pueda abrirlos. **Los selectores se filtran con el mismo scope que los
> listados.**

## 4. Casos especiales

### 4.1 Acceso después de terminar la asignación

| Situación | Decisión | Justificación |
|---|---|---|
| El profesional deja de atender al alumno | **Pierde** acceso a las notas **futuras** | La necesidad operational terminó |
| Notas ya escritas por él | **Conserva** acceso | Su trabajo histórico es suyo; puede necesitar consultarlo para informes |
| El alumno es reasignado a otro profesional | El anterior **no** accede a las notas nuevas | Privacidad del alumno |
| Dirección | Acceso **solo** con grant | Separación de poderes |

**Implementación:** la asignación vigente se evalúa **a la fecha de la nota**, no a la
fecha actual, para las notas ya existentes:

```php
public function hasActiveClinicalAssignmentFor(int $studentId): bool
{
    return DB::connection('scheduling')
        ->table('professional_assignments')
        ->where('professional_id', $this->professional_id)
        ->where('student_id', $studentId)
        ->where(fn ($q) => $q->whereNull('valid_until')->orWhere('valid_until', '>=', today()))
        ->exists();
}
```

> La regla de "conserva sus notas propias" se cubre por el hecho de que **el autor siempre
> accede a su nota** (primera rama de la Policy). Es simple y suficiente.

### 4.2 Acceso a datos de un tercero (familiar que paga)

Ver P9 en [[01.07 Preguntas Abiertas y Decisiones Pendientes]]. Regla provisional:

- Un tutor **no** tiene cuenta de usuario en el MVP.
- Los pagos los registra el personal autorizado.
- Cuando exista el portal familiar, la autorización se modela con un token por cuenta
  familiar y un permiso `family.portal.access`.

### 4.3 Acceso post-mortem o porDbaja de personal

Si un profesional se va del centro:
1. Se desactiva su usuario (`status = 'inactive'`).
2. Se cierran sus asignaciones profesionales (`valid_until = fecha_baja`).
3. Se reasignan los planes de atención donde era responsable.
4. Se revisan los borradores de notas que dejó (quedan `draft`, sin finalized_at).
   - **Decisión pendiente:** ¿se notifica al responsable del plan o se notifica a Dirección?

## 5. Verificación en la CI

Cada Policy debe tener **al menos un test por rama**.

```php
describe('ClinicalNotePolicy', function () {
    it('permite al autor ver su propia nota', ...);
    it('permite al profesional asignado ver la nota', ...);
    it('niega al profesional no asignado', ...);
    it('niega a quien no tiene el permiso', ...);
    it('permite con grant vigente', ...);
    it('niega con grant expirado', ...);
    it('niega con grant revocado', ...);
    it('niega a finanzas', ...);
    it('niega a recepcion', ...);
    it('niega a administracion tecnica', ...);
});
```

**Cobertura mínima:** 100% de las Policies de `care` y `billing`. Para el resto, todas las
ramas de denegación.

**Test universal de denegación por defecto:**

```php
it('niega el acceso por defecto a usuarios sin rol', function () {
    $usuario = User::factory()->create();   // sin roles

    expect($usuario->can('view', $nota))->toBeFalse();
});
```

## 6. Checklist de autorización para un recurso nuevo

- [ ] ¿Existe la Policy con todos los métodos de la acción?
- [ ] ¿El permiso se verifica primero en cada método?
- [ ] ¿Hay un método para el alcance (scope) si aplica?
- [ ] ¿El listado usa el scope?
- [ ] ¿Los selectores del formulario usan el scope?
- [ ] ¿La exportación usa el scope?
- [ ] ¿La búsqueda global incluye o excluye este recurso, de forma consciente?
- [ ] ¿La acción de escritura exige motivo si es de alto impacto?
- [ ] ¿La lectura (si es sensible) se audita?
- [ ] ¿Hay un test por rama de la Policy?
- [ ] ¿`delete` devuelve `false`?
