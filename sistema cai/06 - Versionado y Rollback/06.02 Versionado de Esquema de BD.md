# Versionado de Esquema de BD

> [!important] Principio
> El esquema de la base de datos **no tiene versión propia**. Se versiona con el código
> que lo usa. Esto elimina la necesidad de herramientas de versionado de esquema
> (Liquibase, Flyway, Atlas) y hace imposible la divergencia entre "versión de base" y
> "versión de código".

---

## 1. Cómo funciona

| Concepto | Implementación |
|---|---|
| El esquema vive en el repositorio | Migraciones en `packages/*/database/migrations/` |
| El orden de aplicación | Por la fecha del nombre del archivo |
| El registro de lo aplicado | Tabla `migrations` de Laravel |
| La identidad del esquema | El hash de las migraciones aplicadas |
| La compatibilidad | Garantizada por expand–contract |

```bash
php artisan migrate:status
```

```
+---------------------+---------------------------+---------------------+------------------+
| Migration           | Batch                    | Ran At             | Migration Total  |
+---------------------+---------------------------+---------------------+------------------+
| 2026_02_10_090000_..._create_identity_users | 1 | 2026-02-10 09:01:12 | 15 |
| 2026_02_18_110000_..._create_students_students | 1 | ... | 16 |
+---------------------+---------------------------+---------------------+------------------+
```

## 2. Anatomía de una migración

```php
<?php

declare(strict_types=1);

use Illuminate\Database\Migrations\Migration;
use Illuminate\Database\Schema\Blueprint;
use Illuminate\Support\Facades\Schema;

/**
 * Agrega el índice de vencimientos en billing.charges.
 *
 * Release: cai/billing@v1.3.0
 * Contractual: compatible con cai/billing@v1.2.x (solo agrega un índice)
 */
return new class extends Migration
{
    public function up(): void
    {
        Schema::connection('billing')->table('charges', function (Blueprint $table): void {
            $table->index(['status', 'due_date'], 'charges_status_due_date_idx');
        });
    }

    public function down(): void
    {
        Schema::connection('billing')->table('charges', function (Blueprint $table): void {
            $table->dropIndex('charges_status_due_date_idx');
        });
    }
};
```

### 2.1 Reglas

| Regla | Detalle |
|---|---|
| **Clase anónima** (`return new class extends Migration`) | Laravel 11 lo prefiere; evita colisiones de nombre |
| `declare(strict_types=1)` | Siempre |
| La conexión es explícita | `Schema::connection('billing')` — nunca el default |
| El `down()` existe y hace lo inverso | Probado en CI con `migrate:rollback` en un entorno efímero |
| El nombre describe la acción | `..._create_students_students_table` |
| Las fechas son reales, no inventadas | `2026_02_10_090000` = fecha en que se escribió |

## 3. Nombres de migración

**Formato:** `AAAA_MM_DD_HHMMSS_<schema>_<accion>_<detalle>.php`

```text
2026_02_10_090000_identity_create_users_table
2026_02_18_110000_students_create_students_table
2026_03_01_140000_students_create_family_accounts_table
2026_03_05_093000_billing_add_status_to_charges
2026_04_12_160000_care_add_encrypted_content_to_clinical_notes
2026_06_20_101500_scheduling_add_exclusion_constraint_on_session_professionals
```

| Parte | Significado |
|---|---|
| `AAAA_MM_DD_HHMMSS` | Timestamp de creación. **Determina el orden** |
| `<schema>` | Schema afectado: `identity`, `students`, `scheduling`, `care`, `billing`, `documents`, `notifications`, `reporting` |
| `<accion>` | `create`, `add`, `alter`, `drop`, `seed` |
| `<detalle>` | Nombre de la tabla o columna |

> [!tip] El prefijo del schema no ordena las migraciones
> El orden real es **solo** por timestamp. El prefijo del schema es para que un humano
> pueda leer la lista y entender a qué módulo pertenece cada una. No hay requisito de
> que las migraciones de un schema sean contiguas.

## 4. El problema del `migrate:fresh`

> [!danger] Gotcha G1 — `migrate:fresh` NO borra los schemas de los módulos
> Laravel ejecuta `DROP TABLE` sobre las tablas que conoce, pero **no conoce** las tablas
> de los schemas de los paquetes (no están en el registro `migrations` con su nombre
> cualificado). Resultado: quedan tablas viejas y las migraciones fallan con
> "relation already exists".

**Comando correcto en desarrollo y testing:**

```bash
php artisan cai:db:reset
```

**Qué hace:**

```php
// packages/core/src/Console/Commands/ResetDatabase.php
final class ResetDatabase extends Command
{
    protected $signature = 'cai:db:reset {--force : No pedir confirmación}';

    protected $description = 'Elimina y recrea todos los schemas de los módulos y ejecuta las migraciones';

    public function handle(): int
    {
        if (! $this->option('force') && ! $this->confirm('Esto borra TODOS los datos. ¿Continuar?')) {
            return self::FAILURE;
        }

        $schemas = config('cai.schemas');   // ['identity','students','scheduling','care','billing','documents','notifications','reporting']

        foreach ($schemas as $schema) {
            DB::statement("DROP SCHEMA IF EXISTS {$schema} CASCADE");
            DB::statement("CREATE SCHEMA {$schema}");
        }

        // La tabla de migraciones también se recrea (está en el schema public).
        DB::table('migrations')->truncate();

        $this->call('migrate', ['--force' => true]);

        $this->components->info('Base de datos reconstruida.');

        return self::SUCCESS;
    }
}
```

> [!warning] Nunca en producción
> `cai:db:reset` es **peligroso** y no debe ejecutarse en producción. El comando pide
> confirmación y, si el ambiente es `production`, **se niega a ejecutar** salvo que se
> pase `--force` Y una variable de entorno adicional:
>
> ```php
> if (app()->environment('production') && ! env('CAI_ALLOW_DESTRUCTIVE_RESET')) {
>     $this->components->error('Operación prohibida en producción.');
>     return self::FAILURE;
> }
> ```

## 5. Migraciones que agregan datos (backfill)

### 5.1 Regla

> **Una migración no modifica datos existentes.**
> Las migraciones cambian la **estructura**. Los datos se transforman con **jobs**.

Motivo: una migración que transforma 300 filas puede tardar; una que transforma 100.000
puede **bloquear la tabla** y deixar el deploy colgado.

### 5.2 El patrón correcto

**Paso 1 — Migración que agrega la columna vacía (expand):**

```php
public function up(): void
{
    Schema::connection('billing')->table('charges', function (Blueprint $table): void {
        $table->decimal('paid_amount', 14, 2)->nullable()->default(0);
    });
}
```

**Paso 2 — Job que rellena (migrate):**

```php
// packages/billing/src/Jobs/BackfillChargePaidAmount.php
final class BackfillChargePaidAmount implements ShouldQueue
{
    use Dispatchable, InteractsWithQueue, Queueable;

    public function handle(): void
    {
        DB::connection('billing')->table('charges')
            ->whereNull('paid_amount')
            ->orderBy('id')
            ->chunkById(500, function ($charges): void {
                foreach ($charges as $charge) {
                    $paid = DB::connection('billing')->table('payment_allocations')
                        ->where('charge_id', $charge->id)
                        ->sum('amount');

                    DB::connection('billing')->table('charges')
                        ->where('id', $charge->id)
                        ->update(['paid_amount' => $paid]);
                }
            });
    }
}
```

**Paso 3 — Job que cambia el código para usar la columna (migrate):**

```php
// Ahora el código lee paid_amount en lugar de calcularlo.
$charge->paid_amount;
```

**Paso 4 — Migración que pone `NOT NULL` y elimina lo viejo (contract):**

```php
public function up(): void
{
    Schema::connection('billing')->table('charges', function (Blueprint $table): void {
        $table->decimal('paid_amount', 14, 2)->nullable(false)->default(0)->change();
    });
}
```

## 6. Cambios sensibles y cómo hacerlos

| Cambio | ¿Se permite en un solo release? | Cómo |
|---|---|---|
| Agregar columna `nullable` | ✅ Sí | Directo |
| Agregar columna con default | ✅ Sí | Directo |
| Agregar columna `NOT NULL` sin default | ⚠️ Con cuidado | Agregar nullable → backfill → `NOT NULL` |
| Cambiar tipo de columna | ❌ No | Columna nueva → backfill → código → eliminar vieja |
| Renombrar columna | ❌ No | Igual que cambiar tipo |
| Eliminar columna | ❌ No | Primero el código deja de usarla (1 release) |
| Agregar índice | ✅ Sí | `CREATE INDEX CONCURRENTLY` si la tabla es grande |
| Agregar FK | ⚠️ Con cuidado | Validar datos antes |
| Agregar `CHECK` | ⚠️ Con cuidado | Validar datos antes |
| Cambiar un `enum` | ⚠️ Con cuidado | `ALTER TYPE ... ADD VALUE` (no se puede quitar en la misma tx) |
| Agregar `NOT NULL` con default en tabla grande | ⚠️ | Postgres 11+ lo hace rápido, pero validar |

### 6.1 `CREATE INDEX CONCURRENTLY`

```php
public function up(): void
{
    // CONCURRENTLY no puede ejecutarse dentro de una transacción.
    DB::connection('billing')->statement(
        'CREATE INDEX CONCURRENTLY IF NOT EXISTS charges_family_status_idx
         ON billing.charges (family_account_id, status)'
    );
}

public function down(): void
{
    DB::connection('billing')->statement(
        'DROP INDEX CONCURRENTLY IF EXISTS billing.charges_family_status_idx'
    );
}
```

> [!warning] La migración se ejecuta fuera de la transacción
> Laravel envuelve las migraciones en una transacción por defecto. Para las que
> necesitan `CONCURRENTLY`, la propiedad `$withinTransaction = false`:
>
> ```php
> public bool $withinTransaction = false;
> ```

## 7. Verificación del esquema

### 7.1 Comandos útiles

```bash
# Estado de las migraciones
php artisan migrate:status

# Ver el esquema resultante de un schema
psql -d cai -c '\d+ billing.charges'

# Listar todos los schemas y sus tablas
psql -d cai -c "SELECT table_schema, count(*) FROM information_schema.tables
                WHERE table_schema NOT IN ('pg_catalog','information_schema')
                GROUP BY 1 ORDER BY 1;"

# Ver los índices de una tabla
psql -d cai -c '\di billing.*'

# Ver las restricciones de exclusión
psql -d cai -c "SELECT conname, pg_get_constraintdef(oid) FROM pg_constraint
                WHERE contype='x' AND connamespace='scheduling'::regnamespace;"
```

### 7.2 Test de verificación del esquema

```php
// tests/Feature/SchemaStructureTest.php
it('has one schema per module', function () {
    $schemas = DB::select(
        "SELECT schema_name FROM information_schema.schemata
         WHERE schema_name NOT IN ('public','pg_catalog','information_schema')
         AND schema_name NOT LIKE 'pg_%' ORDER BY 1"
    );

    expect(collect($schemas)->pluck('schema_name')->all())
        ->toEqual(config('cai.schemas'));
});

it('has no foreign keys from care to billing', function () {
    $violations = DB::select(
        "SELECT conname FROM pg_constraint
         WHERE contype = 'f'
           AND connamespace = 'care'::regnamespace
           AND confrelid::regnamespace::text LIKE 'billing%'"
    );

    expect($violations)->toBeEmpty();
});
```

## 8. Ambientes y el esquema

| Ambiente | Cómo se construye | Datos |
|---|---|---|
| **local** | `cai:db:reset` + seeds | Ficticios |
| **testing** | `cai:db:reset` en la CI | Ficticios |
| **staging** | `cai:db:reset` + carga anonimizada de producción | Anonimizados |
| **producción** | `php artisan migrate` (aplicar, nunca reset) | Reales |

> [!danger] En producción solo `migrate`
> `cai:db:reset` en producción **destruye todos los datos**. El comando lo bloquea. Los
> backups se toman antes de cada migración en producción (ver [[06.07 Backups y Recuperación]]).

## 9. Checklist de migración

- [ ] ¿Es una migración **nueva**? (no edito una aplicada)
- [ ] ¿Usa la conexión explícita del schema?
- [ ] ¿Tiene `down()`?
- [ ] ¿Es compatible con el release anterior?
- [ ] ¿El `down()` fue probado?
- [ ] ¿Bloquea la tabla? Si sí, ¿es aceptable en el horario del deploy?
- [ ] ¿Toca datos existentes? Si sí, ¿es un job y no la migración?
- [ ] ¿Hay un índice que se pueda agregar en `CONCURRENTLY`?
- [ ] ¿Se probó en staging con datos realistas?
- [ ] ¿El `down()` fue probado?
