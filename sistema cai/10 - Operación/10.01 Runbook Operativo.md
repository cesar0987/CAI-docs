# Runbook Operativo

> [!danger] El documento más importante para la continuidad
> Este runbook existe para que **el sistema pueda operarse sin el desarrollador**.
> Si la única persona que entiende el sistema es quien lo escribió, el sistema tiene
> un punto único de falla que no es técnico: es humano.
>
> **Regla del runbook:** cada procedimiento está escrito para que alguien que nunca
> lo hizo pueda seguirlo y obtener el resultado esperado.

---

## 1. A quién sirve este runbook

| Rol | Qué hace con este runbook |
|---|---|
| **Administración Técnica** | Opera el sistema: deploys, backups, rollback, incidentes |
| **Dirección** | Decide en los incidentes que requieren criterio de negocio |
| **Backup Custodian** | Custodia las claves y verifica los backups externos |
| **El desarrollador** | Lo mantiene actualizado |

> [!important] El runbook es un documento vivo
> Cada incidente o cambio importante **actualiza** este documento. Un runbook con
> seis meses sin tocarse es un runbook que ya no describe el sistema.

## 3. Routine: el día a día

### 3.1 Cada mañana (2 minutos)

```bash
ssh usuario@SERVIDOR
cd /srv/cai
sudo ./scripts/healthcheck.sh
```

Todos deben decir `OK`. Si algo falla, ir a §7.

### 3.2 Cada semana (10 minutos)

```text
☐ Revisar el backup externo (que llegó y se puede restaurar)
☐ Revisar el log de errores de la semana
☐ Verificar el espacio en disco
☐ Revisar el estado de los jobs en cola
```

Procedimiento completo en [[10.02 Calendario de Checklists]].

### 3.3 Cada mes (30 minutos)

```text
☐ "Día del administrador" (versión corta): backups, disco, base de datos
☐ Revisar la auditoría de accesos clínicos
☐ Limpiar releases antiguos
☐ Revisar los paquetes de dependencias con actualizaciones de seguridad
```

## 4. Procedimiento: desplegar una versión nueva

> [!danger] Antes de empezar
> - [ ] La CI está **verde** en `main`.
> - [ ] Hay un backup **de hoy** verificado.
> - [ ] Nadie está en mitad de una tarea crítica.
> - [ ] Se conoce el comando de **rollback**.

### 4.1 El procedimiento

```bash
# 1. Estado actual (anotarlo: si hay que volver, es a esto)
cd /srv/cai
sudo ./scripts/status.sh

# 2. Traer la versión
cd /srv/cai/current
git fetch --all --tags
git checkout main
git pull origin main

# 3. Instalar dependencias (sin scripts)
composer install --no-dev --optimize-autoloader --no-scripts

# 4. Crear el release
cd /srv/cai
sudo ./scripts/release.sh deploy --version=$(git -C current rev-parse --short HEAD)

# 5. Verificar
sudo ./scripts/healthcheck.sh
curl -s http://127.0.0.1:8000/up
```

### 4.2 Lo que hace `release.sh`

```text
1. Verifica que la CI está verde (consulta el estado de GitHub)
2. Crea /srv/cai/releases/{timestamp}-{version}/
3. Copia los archivos (o hace git clone del tag)
4. Enlaza storage/ y .env desde /srv/cai/shared/
5. Ejecuta composer install --no-dev
6. Ejecuta php artisan migrate --force
7. Ejecuta php artisan config:cache && route:cache && view:cache
8. Ejecuta php artisan queue:restart
9. Cambia el symlink current → nuevo release
10. Cambia el symlink previous → release anterior
11. Ejecuta healthcheck
12. Si falla, hace rollback automático
```

> [!important] El rollback automático es la red de seguridad
> Si el healthcheck final falla, `release.sh` **vuelve automáticamente** al release
> anterior. Un deploy a ciegas es un deploy sin red.

### 4.3 Verificar después de desplegar

```bash
# 1. La aplicación responde
curl -s http://127.0.0.1:8000/up

# 2. El symlink apunta al release nuevo
ls -la /srv/cai/current

# 3. Los logs no tienen errores nuevos
sudo tail -n 30 /srv/cai/shared/storage/logs/laravel.log

# 4. Entrar al panel con un usuario real y probar el flujo principal
```

## 5. Procedimiento: rollback

> [!danger] El rollback es la primera respuesta a un problema
> Si la aplicación está rota en producción, **primero** se hace rollback, después se
> investiga. Investigar con el centro esperando es la peor forma de investigar.

### 5.1 Cuándo hacer rollback

| Situación | ¿Rollback? |
|---|---|
| Error 500 generalizado tras un deploy | ✅ **Sí, inmediatamente** |
| Una funcionalidad nueva está rota | ✅ Sí (si hay flag, apagar el flag es aún mejor) |
| Un dato quedó mal escrito | ⚠️ No: se corrige el dato |
| El servidor está lento | ⚠️ No: se investiga |
| Un usuario no puede entrar | ❌ No: puede ser su contraseña |

### 5.2 El procedimiento

```bash
# 1. Ver el estado
cd /srv/cai
sudo ./scripts/status.sh

# 2. Rollback
sudo ./scripts/rollback.sh

# 3. Verificar
sudo ./scripts/healthcheck.sh
curl -s http://127.0.0.1:8000/up
sudo tail -n 20 /srv/cai/shared/storage/logs/laravel.log
```

### 5.3 Lo que hace `rollback.sh`

```text
1. Identifica el release actual y el anterior (symlink previous)
2. Verifica que el release anterior existe y está completo
3. Cambia el symlink current → release anterior
4. Ejecuta php artisan config:cache, route:cache, queue:restart
5. Ejecuta el healthcheck
6. NO toca la base de datos
```

> [!important] El rollback no revierte la base de datos
> Por eso las migraciones usan el patrón **expand–contract**: una versión nueva
> nunca rompe a la anterior. Si el rollback no resuelve el problema, el siguiente
> nivel es restaurar el backup. Ver [[06.06 Procedimiento de Rollback]] y
> [[10.04 Recuperación ante Desastres]].

### 5.4 Cuándo hay que restaurar el backup

| Situación | Nivel |
|---|---|
| Error de código | **1.** Rollback de código (~1 min) |
| Bug de código | **1.** Rollback de código |
| Flag de una funcionalidad | **0.** Kill switch (inmediato) |
| Dato corrupto por una migración | **2.** Restaurar `pg_dump` pre-release |
| Ransomware o daño al disco | **3.** Restaurar backup externo cifrado |
| Desastre total del servidor | **4.** Servidor nuevo + backup externo |

## 6. Procedimiento: backup y verificación

### 6.1 El backup diario automático

```bash
# Cron: /etc/cron.d/cai-backup
0 2 * * * root /srv/cai/scripts/backup.sh >> /var/log/cai/backup.log 2>&1
0 3 * * * root /srv/cai/scripts/backup-external.sh >> /var/log/cai/backup-external.log 2>&1
```

### 6.2 Verificar que el backup existe

```bash
ls -lh /var/backups/cai/
tail -n 20 /var/log/cai/backup.log
```

### 6.3 Verificar que el backup se PUEDE restaurar

> [!danger] Un backup que no se ha restaurado no es un backup
> Es una **esperanza**. La verificación real es restaurar y arrancar. Se hace
> mensualmente en un entorno de pruebas.

```bash
# Restaurar en una base de datos aparte y verificar
sudo ./scripts/restore-from-dump.sh --verify-latest --target=cai_verify
```

### 6.4 La lista de verificación del backup externo

```text
☐ El archivo llegó al destino externo
☐ El tamaño es el esperado (no 0 bytes)
☐ Se puede abrir con la clave de descifrado
☐ La fecha del archivo es la esperada
☐ La clave está en el gestor de contraseñas (no en el servidor)
```

> [!danger] La clave y el backup van separados
> El backup cifrado **nunca** está en el mismo lugar que la clave de cifrado. Si
> están juntos, el cifrado no protege nada. Ver [[06.07 Backups y Recuperación]].

## 7. Procedimiento: incidentes

| Severidad | Definición | Tiempo de respuesta | Quién |
|---|---|---|---|
| 🔴 **Crítico** | El centro no puede operar | 15 min | Admin Técnico + Dirección |
| 🟡 **Alto** | Una parte importante no funciona | 2 h | Admin Técnico |
| 🟢 **Medio** | Molestia, hay alternativa | 1 día | Admin Técnico |
| ⚪ **Bajo** | Mejora o duda | 1 semana | Backlog |

**El flujo completo está en [[10.03 Gestión de Incidentes]].**

### 7.1 Los primeros 5 minutos ante un incidente crítico

```text
1. NO entrar en pánico. Anotar la hora exacta.
2. ¿El sistema entero está caído o solo una parte?
3. Si es solo una parte: ¿hay un interruptor que la apague?
4. Si es el sistema entero: ¿se puede hacer rollback?
5. Si nada funciona: restaurar el backup. (10.04)
6. Avisar a Dirección si el centro no puede operar.
```

## 8. Procedimiento: gestión de usuarios de emergencia

> [!danger] Si el único administrador técnico no está
> El usuario `admin@cai.local` tiene una contraseña en el gestor de contraseñas del
> centro. **No** está en este documento.

```text
1. Buscar en el gestor de contraseñas: "CAI admin emergencia"
2. Iniciar sesión con esa cuenta
3. Verificar: Panel → Administración → Usuarios
4. Si funciona: el problema es la cuenta del técnico, no el sistema
5. Si no funciona: restaurar el backup (10.04)
```

## 9. Los comandos de referencia

```bash
# --- Estado ---
sudo ./scripts/status.sh              # Tablero de estado
sudo ./scripts/healthcheck.sh         # Verificación de salud

# --- Deploy y rollback ---
sudo ./scripts/release.sh deploy      # Desplegar
sudo ./scripts/rollback.sh             # Volver atrás
sudo ./scripts/prune-releases.sh --keep 5

# --- Backups ---
sudo ./scripts/backup.sh               # Backup local
sudo ./scripts/backup-external.sh      # Backup externo cifrado
sudo ./scripts/restore-from-dump.sh --file=/var/backups/cai/xxx.dump

# --- Logs ---
sudo tail -f /srv/cai/shared/storage/logs/laravel.log
sudo tail -f /var/log/nginx/error.log
sudo journalctl -u php8.3-fpm -f

# --- Base de datos ---
sudo -u postgres psql -d cai
sudo -u postgres psql -d cai -c "SELECT count(*) FROM identity.users;"
sudo -u postgres pg_dump -d cai -n identity -Fc -f /tmp/identity.dump
```
