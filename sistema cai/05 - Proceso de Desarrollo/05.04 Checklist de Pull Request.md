# Checklist de Pull Request

> [!important] Cómo se usa
> Con un solo desarrollador, la revisión es **auto-revisión**. Para que funcione, la
> checklist se completa **explícitamente en el cuerpo del PR**, marcando cada casilla.
> Escribir la casilla es lo que produce el beneficio; tenerla en la cabeza, no.

---

## 1. Plantilla del Pull Request

```markdown
## Descripción
<!-- Qué cambia y por qué. En 2-4 líneas. -->

Closes #<número>

## Tipo de cambio
- [ ] Funcionalidad nueva (`feat`)
- [ ] Corrección de bug (`fix`)
- [ ] Documentación (`docs`)
- [ ] Refactorización (`refactor`)
- [ ] Mantenimiento (`chore`)

## Módulos afectados
<!-- Marcar los paquetes involvementados -->
- [ ] `cai/core`
- [ ] `cai/identity`
- [ ] `cai/students`
- [ ] `cai/scheduling`
- [ ] `cai/care`
- [ ] `cai/billing`
- [ ] `cai/documents`
- [ ] `cai/notifications`
- [ ] `cai/reporting`
- [ ] Host (`app/`)

## Checklist de calidad
<!-- Ver sección 2 -->

## Checklist de datos
<!-- Ver sección 3 -->

## Riesgo y rollback
- [ ] ¿Este cambio requiere migración de datos? → **Sí / No**
- [ ] ¿Es compatible con el release anterior? → **Sí / No**
- [ ] ¿Hay feature flag asociado? → **Sí (cuál) / No**
- [ ] ¿Cómo se revierte? → `<descripción>`
```

## 2. Checklist de calidad

### 2.1 Corrección funcional

- [ ] El código hace lo que dice la descripción (revisado, no supuesto)
- [ ] Los casos borde están contemplados
- [ ] Los mensajes de error son accionables y en español
- [ ] No se introducen funcionalidades fuera del alcance del PR
- [ ] Si toca reglas de negocio: **validado por Dirección**

### 2.2 Arquitectura

- [ ] `composer deptrac` pasa — no se cruzaron fronteras entre módulos
- [ ] No hay relaciones Eloquent cross-módulo
- [ ] La lógica de negocio **no** está en las clases de Filament
- [ ] Las Actions de negocio se invocan desde la interfaz
- [ ] Cada modelo declara `protected $connection`
- [ ] No hay `DB::raw()` fuera de migraciones
- [ ] No hay `select *` en consultas

### 2.3 Base de datos

- [ ] Las migraciones son **nuevas** (no se editaron migraciones ya aplicadas)
- [ ] La migración es **compatible con el release anterior** (expand–contract)
- [ ] Las claves foráneas tienen `ON DELETE` explícito
- [ ] Las columnas con conjunto cerrado tienen `CHECK`
- [ ] Los índices cubren las consultas de lectura nuevas
- [ ] La migración tiene `down()` probado
- [ ] Si hay una restricción de exclusión, se probó el caso de solapamiento

### 2.4 Seguridad

- [ ] Toda acción sensible valida permisos (`Gate::authorize()`)
- [ ] Los listados y selectores aplican el **scope** del usuario
- [ ] Las operaciones de alto impacto exigen **motivo**
- [ ] No se registran datos sensibles en logs
- [ ] No se exponen datos clínicos o financieros en la interfaz sin el permiso
- [ ] Los inputs del usuario se validan
- [ ] No hay secretos en el código

### 2.5 Calidad del código

- [ ] `composer lint` pasa (Pint)
- [ ] `composer analyse` pasa (Larastan nivel 5)
- [ ] Tipos de retorno declarados en todos los métodos públicos
- [ ] `declare(strict_types=1);` presente
- [ ] Sin `dd()`, `dump()`, `var_dump()`, código muerto ni `TODO` sin contexto
- [ ] Los nombres son autoexplicativos (no hay `data2`, `tmp`, `helper`)
- [ ] La duplicación evitada (si hay, está justificada en un comentario)

### 2.6 Tests

- [ ] `composer test` pasa
- [ ] Hay test para el comportamiento **nuevo**
- [ ] Hay test para el **caso borde** principal
- [ ] Hay test de **autorización** si el PR toca un recurso protegido
- [ ] Hay test de **regresión** si el PR corrige un bug (reproduce el bug)
- [ ] Los tests no dependen del orden de ejecución
- [ ] No hay tests que dependan de la fecha real (usar `freezeTime()`)

### 2.7 Documentación

- [ ] El CHANGELOG se genera automáticamente (no se edita a mano)
- [ ] Si hay un cambio estructural → **hay un ADR**
- [ ] Si cambia un requerimiento → se actualiza [[01.05 Requisitos Funcionales]]
- [ ] Si cambia una regla de negocio → se actualiza [[01.04 Reglas de Negocio]]
- [ ] Si toca el plan → se actualiza el documento de la fase en `08 - Plan de Trabajo`
- [ ] Los cambios de la API de un paquete están documentados en su README

## 3. Checklist de datos

### 3.1 Migraciones

| Aspecto | Regla |
|---|---|
| ¿Es una migración nueva? | Sí. Nunca se edita una aplicada |
| ¿Es compatible hacia atrás? | El release anterior debe seguir funcionando |
| ¿Es compatible hacia adelante? | El release nuevo debe funcionar con el schema viejo (durante el deploy) |
| ¿Tiene `down()`? | Sí, y probado |
| ¿Toca datos existentes? | Si sí, es un **backfill** y va en un job, no en la migración |
| ¿Requiere ventana de mantenimiento? | Si sí, se documenta en el PR |

**Ejemplo de incompatibilidad — NO hacer esto:**

```php
// ❌ Rompe el release anterior
$table->renameColumn('name', 'full_name');
// ❌ Rompe el release anterior
$table->dropColumn('legacy_code');
// ❌ Rompe el release anterior
$table->string('status')->change();
```

**Lo correcto (expand–contract):**

```php
// ✅ Release N (expand): se agrega la columna nueva, la vieja sigue existiendo
$table->string('full_name')->nullable()->after('name');

// ✅ Release N+1 (migrate): el backfill en un job
// ✅ Release N+2 (contract): se elimina la columna vieja
```

Ver [[06.03 Expand-Contract]].

### 3.2 Contenido sensible

- [ ] Ningún dato clínico en logs, en errores ni en mensajes de la UI
- [ ] Los datos personales no aparecen en las URLs
- [ ] Las exportaciones respetan los permisos del usuario
- [ ] Los backups de este PR, si los hay, están cifrados

---

## 4. Checklist de despliegue

- [ ] ¿Requiere migraciones? → **Sí / No**
- [ ] ¿Requiere nuevas variables de entorno? → **Sí (cuáles) / No**
- [ ] ¿Requiere feature flag activado? → **Sí (cuál) / No**
- [ ] ¿Requiere comando de post-deploy? → **Sí (cuál) / No**
- [ ] ¿Hay riesgo para la operación? → **Sí (cuál) / No**
- [ ] ¿Cómo se revierte este cambio?

---

## 5. Checklist de rollback

Todo PR debe tener una respuesta clara a: *"¿cómo deshago esto?"*

| Tipo de cambio | Cómo se revierte |
|---|---|
| Solo código | Mergear un revert / desplegar el release anterior |
| Código + migración compatible | Desplegar el release anterior (la migración no se revierte) |
| Código + migración destructiva | **No se permite** sin expand–contract |
| Feature flag | Apagar el flag (instantáneo) |
| Datos | Script de corrección documentado |
| Configuración | Revertir el valor en `settings` |

---

## 6. Checklist de rollback — preguntas de escape

> Si alguna de estas preguntas es "sí", el PR **no** se mergea:

- [ ] ¿El release anterior deja de funcionar con este schema? → **Debe ser NO**
- [ ] ¿Se editó una migración ya aplicada? → **Debe ser NO**
- [ ] ¿Hay datos que se perderían si se revierte? → **Debe ser NO** (o documentado)
- [ ] ¿Se rompe alguna frontera entre módulos? → **Debe ser NO**
- [ ] ¿Un rol sin permiso ve información sensible nueva? → **Debe ser NO**
- [ ] ¿El PR tiene más de 800 líneas? → **Debe ser NO** (dividir)

---

## 7. Plantilla de checklist rápido

Para PRs pequeños (< 50 líneas, sin migraciones), se puede usar esta versión:

```markdown
- [ ] `lint` `analyse` `deptrac` `test` en verde
- [ ] Sin fronteras cruzadas
- [ ] Sin lógica de negocio en Filament
- [ ] Autorización verificada (si aplica)
- [ ] Test del comportamiento nuevo
- [ ] Compatible con el release anterior
- [ ] Cómo se revierte: <descripción>
```
