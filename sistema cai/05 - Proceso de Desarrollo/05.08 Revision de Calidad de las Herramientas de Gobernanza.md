> El **diagnóstico verificado** del código que hace cumplir la gobernanza del

## 1. Resumen ejecutivo

El diseño de la gobernanza es correcto: registro append-only, atribución de IA,
verificación automática e IDs estables. **La implementación no está a la altura
del diseño.** Dos herramientas pueden destruir o validar mal el histórico, y la
misma política está escrita tres veces con reglas que ya no coinciden.

| Principio | Veredicto | Nota | Evidencia principal |
|---|---|---|---|
| **SOLID** | ⚠️ Parcial | 2 / 5 | `main()` y los subcomandos acumulan 6–8 responsabilidades; el I/O y `sys.exit()` están dentro de la lógica, así que nada se puede probar (HC-09, HC-11) |
| **DRY** | ❌ No cumple | 1 / 5 | La política vive en 3 motores divergentes (HC-03); parseo de enlaces, formato de modelo, flujo de registro y `env` de CI duplicados (HC-08, HC-09, HC-20) |
| **KISS** | ⚠️ Parcial | 3 / 5 | Scripts sin dependencias y con salida clara, pero `insertar_en_indice` usa aritmética de offsets y el plugin adivina commits por regex (HC-05, HC-17) |
| **YAGNI** | ⚠️ Parcial | 3 / 5 | `ci.yml` y `deptrac.yaml` describen código que no está en este repositorio; ramas y retornos muertos (HC-07, HC-10, HC-15) |
| **Clean Code** | ❌ No cumple | 1 / 5 | 0 pruebas sobre 1.150 líneas que hacen cumplir la política; comentarios que afirman lo contrario de lo que hace el código; comandos documentados que fallan (HC-06, HC-10, HC-13) |
| **Robustez** *(criterio adicional)* | ❌ No cumple | 1 / 5 | Un bug borra entradas de la bitácora y otro valida el mensaje del commit anterior (HC-01, HC-02) |

> [!danger] Lo que hay que arreglar primero
> **HC-01** (el plugin borra el bloque de sesiones) y **HC-02** (el hook valida
> el mensaje anterior) no son deuda de estilo: son fallas que ya produjeron
> pérdida de datos y que dejaban pasar commits sin verificación real.
> **T1 los corrigió el 2026-10-22** (ver §6); T2–T4 siguen abiertas.

  una falta: es una deuda con ubicación y corrección propuestas.

  cambia, el ID del hallazgo sigue siendo válido aunque la línea se mueva.

## 3. Veredicto por principio

### 3.1 SOLID — 2 / 5

Lo que no:

| Complejidad innecesaria | Ubicación | Alternativa simple |
|---|---|---|

### 4.1 Detalle de los P0

#### HC-01 · El plugin destruye el histórico

La función dice “inserta”, pero descarta todo lo que está entre los dos marcadores:

```ts
const head = content.slice(0, i + start.length)
const tail = content.slice(j)            // descarta el bloque anterior completo
return `${head}\n${block}\n${tail}`
```

La llamada de `:309` usa los marcadores `SES-ENTRIES`, así que **cada sesión
cerrada automáticamente reemplaza todas las anteriores**. Contradice el
docstring del propio plugin (`:18`), [[12.01 Política de Cambios y Trazabilidad]]
§3 y AGENTS.md §1. Además, al borrar también el marcador
`<!-- SES-<sessionID> -->`, la comprobación de idempotencia (`:277`) vuelve a
fallar en el commit siguiente: la pérdida se repite.

#### HC-02 · El hook valida el mensaje anterior

`pre-commit` corre **antes** de que Git obtenga el mensaje. Lo que hay en
`COMMIT_EDITMSG` en ese momento es el mensaje del commit anterior. Prueba en un
repositorio desechable:

```text
commit 1 → HOOK-VE: []
commit 2 → HOOK-VE: [primer mensaje REG-2026-001]
```

En este repositorio, `.git/COMMIT_EDITMSG` contiene hoy
`docs: REG-2026-009 close CAI session tracking`. Un commit con un REG
inexistente pasaría, porque el hook encontraría el ID del commit anterior.

#### HC-03 · Tres motores, tres respuestas

| Comprobación | `pre-commit` | Plugin | `cai-log.py` |
|---|---|---|---|
| Cita un REG | Sí | Sí | No aplica |
| El REG existe | Encabezado `^## REG` | Subcadena en el texto | Encabezado `^## REG` |
| Borrados | Solo advierte | Bloquea | No aplica |
| Formato de ID de sesión | — | Correlativo de todos los años | Correlativo del año en curso |
| Escape | `CAI_COMMIT_MSG` no documentado | `--no-verify` sugerido en el error | — |

El efecto no es teórico: el hook y el plugin **ya no aplican la misma política**.

#### HC-22 · El correlativo automático siempre devuelve `001`

Verificado durante esta revisión, al intentar registrar el cambio que produce
este documento:

```text
$ bin/cai-log.py cambio --tipo edición --severidad N1 --motivo "..." --seco
ERROR: el ID REG-2026-001 ya existe: el registro es de solo agregar
```

La causa está en `siguiente_id` (`:150`): el patrón usa `^` pero se compila sin
`re.MULTILINE`, así que solo puede coincidir al inicio del texto completo. Como
el registro empieza con el frontmatter, no hay coincidencia y el resultado es
siempre `1`. El control de duplicados (`:229` y `:303`) entonces bloquea toda
alta que no pase `--id` a mano, y `--id` no valida formato (HC-18).

**Efecto:** la numeración depende de que la persona recuerde el último número;
un salto o una repetición no se detectan, y el comando documentado en
`AGENTS.md` §5.1 no funciona tal como está escrito. Las entradas existentes
tienen números correlativos, de modo que el alta se hizo con `--id` explícito y
la falla pasó desapercibida.

## 5. Incidente del 2026-10-22: pérdida de entradas en 12.03

> [!warning] Se registra porque ocurrió
> La bitácora es de solo agregar. Este incidente no se oculta: se documenta con
> causa, efecto y recuperación, según GC-16 y [[12.02 Registro de Cambios]] §1.1.

| Hora (−03) | Hecho |
|---|---|
| 22:02 | Una sesión del agente queda asociada al repositorio con el modelo `opencode/big-pickle#default` |
| 22:04 | Se ejecuta un `git commit` de prueba en un repositorio temporal; el texto del comando contiene la palabra `git commit` |
| 22:04 | El plugin interpreta que se está commiteando en este repositorio (HC-05), no encuentra su marcador de sesión y escribe una entrada nueva |
| 22:04 | `insertBetween` reemplaza el bloque completo (HC-01): desaparecen `SES-2026-004` y `SES-2026-003`, y aparece `SES-2026-005` con objetivo “completar” |
| 22:08 | Se detecta durante la revisión (`git status` con un archivo modificado que estaba limpio al inicio) |
| 22:10 | Se restaura el archivo desde `HEAD` y se verifica que el árbol queda limpio |

**Causa raíz:** HC-01 (reemplazo destructivo) habilitado por HC-05 (detección de
commit por texto) y por HC-04 (escritura durante la validación).

**Recuperación aplicada:** restauración byte a byte desde `HEAD` de
`sistema cai/12 - Registro de Cambios/12.03 Bitácora de Sesiones con IA.md`.
No se perdió ninguna entrada: el contenido previo estaba íntegro en `HEAD`.

**Prevención:** T1 del plan (HC-01, HC-02, HC-03) más la prueba T-21 de
[[05.09 Herramientas de Gobernanza]] §9, que exige que tres entradas previas
sigan intactas después de una inserción.

## 8. Lo que NO se propone (YAGNI aplicado a la corrección)

| Descartado | Por qué |
|---|---|
| Reescribir las herramientas en otro lenguaje | Funcionan y no tienen dependencias; el problema es el diseño, no el lenguaje |
| Adoptar un framework de hooks (`pre-commit`, `lefthook`) | Agrega una dependencia y un archivo de configuración para reemplazar 96 líneas de `bash`; contradice GE-11 |
| Un servidor o servicio para validar | El proyecto es local por diseño; el hook y el script alcanzan |
| Cobertura de pruebas del 100 % | La meta es cubrir las reglas de la matriz de §9, no cada línea |
| Un documento de proceso por hallazgo | Un informe y un contrato alcanzan; el resto vive en el backlog |
| Editar los ADR aceptados para corregir erratas | GC-08: se sustituyen, no se editan; las erratas se listan en §9 |
| Validar también en el CI del repositorio de código | El código de producto no está aquí; ese CI pertenece al otro repositorio (HC-10) |
